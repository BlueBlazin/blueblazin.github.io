Measure Cached Decode Across Lengths

By the end of this hour

  • Measure cached decode across the frozen prompt lengths.
  • Preserve equivalent cache state and report variability.

Before you begin

  • The frozen decode definition and the supplied KV-cache path, with full-sequence versus cached logit parity already passing.
  • Prefill measurement outputs and the same hardware configuration.

Environment or workflow question? Day 0 handbook.

The key idea

Cached decode latency depends on both the prompt length and the evolving generated length. Comparing different cache states or numbers of generated tokens changes the workload. Define whether the measurement includes model execution alone, sampling, or host dispatch, and preserve that boundary across variants. Reinitialize caches consistently for repeated batches so one variant does not inherit a longer history. Report per-token latency only with the exact token-count definition; aggregate throughput and individual-step latency answer different questions. Correct cache updates remain a prerequisite even when the custom kernel only changes normalization.

Your 60-minute plan

  1. Retrieve

    5 min

    Identify which KV-cache dimensions grow with the prompt and generated sequence lengths.

  2. Study

    10 min

    Use the core resources above for ten minutes in total, focusing only on the indicated sections. Revisit K2 measurement guidance and the supplied cached-generation parity smoke; locate any hidden host synchronization in the loop.

  3. Build

    35 min

    For each frozen prompt length, initialize the cache from the same prompt and decode the same fixed number of steps in every variant. Use deterministic token selection or supplied next-token inputs so execution paths remain comparable. Separate cache construction from the decode timer, synchronize at the declared boundary, and repeat matched batches. Record total decode time, the chosen per-token summary, batch variability, and final cache length. Check selected logits or generated tokens against the reference and retain any compiled-mode failure or slowdown. Reinitialize state between repetitions rather than accumulating history accidentally. Run cache construction, warm-up, and timed decode under model.eval() and torch.inference_mode(). Before timing a compiled case, warm that entire prompt-plus-decode trajectory from a reset cache until no new compilation occurs, checking recompilation/graph-break logs outside the timed region. Reusing a prefill-only warm-up is insufficient when cache lengths grow. If a path falls back to eager or continues recompiling, label that result explicitly rather than calling it warmed compiled decode. Keep all lengths within config.max_seq_len.

  4. Verify and save

    10 min

    Save the decode table with exact prompt/output lengths, timing boundary, variability, and correctness status. Export logs and stop the GPU session.

What to save

Decode timing table with variability and unchanged correctness.

Watch for: Prefill-only warm-up may leave decode shapes uncompiled. Do not time recompile or eager-fallback paths as warmed compiled decode, and do not include prefill in a per-token decode latency.

Check your understanding

Why must the cache be reset between repeated decode measurements?

Check your reasoning

Otherwise later repetitions process a longer history, changing both memory traffic and attention work.

Report Whole Model Gains and Regressions

By the end of this hour

  • Report the complete decoder comparison, including regressions.
  • Explain whole-model effects without overstating causality.

Before you begin

  • Saved prefill and decode data for all frozen cases.
  • Your earlier operator microbenchmarks and Amdahl calculation.

Environment or workflow question? Day 0 handbook.

The key idea

End-to-end results are the practical test of a custom kernel, but their interpretation still requires matched conditions. A microbenchmark gain can disappear because normalization occupies little total time, compilation already fuses surrounding work, or dispatch overhead changes. Conversely, a larger-than-expected effect should prompt a check for changed work or fusion before being credited to the kernel alone. Report every frozen case, including failures and slowdowns. Use speedup=treference/tcustom\text{speedup}=t_{\mathrm{reference}}/t_{\mathrm{custom}}speedup=treference​/tcustom​ consistently, and pair ratios with absolute milliseconds so small effects remain understandable.
