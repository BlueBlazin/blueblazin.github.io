Verify the Regression or Support Boundary

By the end of this hour

  • Validate the proposed change with the relevant focused check.
  • Document both the original failure and corrected behavior.

Before you begin

  • The minimal local upstream contribution draft or internal limitation/reproducer from step 16-2.
  • The documented operator contract, smallest failing/limitation input, and relevant focused test command. Consult the target contribution conventions in the shared guide only if this is an upstream patch.

Environment or workflow question? Day 0 handbook.

The key idea

The most persuasive regression evidence shows that the relevant check detects the original problem and passes with the proposed fix under the same conditions. For a documentation or benchmark correction, the analogous evidence is an exact procedure that reproduces the old error and verifies the corrected behavior. Broader testing is useful only when the change touches broader behavior or project rules require it. A local inability to test a hardware-specific path must remain explicit. Do not turn a narrow contribution into a new optimization project during validation.

Your 60-minute plan

  1. Retrieve

    5 min

    Name the specific assertion or observed outcome that separates the original behavior from the proposed fix.

  2. Study

    10 min

    Use the core resources above for ten minutes in total, focusing only on the indicated sections. Read the target project’s relevant test requirements and the surrounding test style, focusing on the changed area.

  3. Build

    35 min

    Run the smallest relevant validation against the original revision and your patched version, keeping environment and inputs fixed. For a regression test, confirm it fails for the intended reason before the fix and passes afterward. For a documentation or benchmark correction, execute the corrected command or recompute the affected result and retain the before/after evidence. Inspect the diff for unintended numerical, layout, or public-interface changes. Fix demonstrated issues only. If required hardware is unavailable, state exactly which checks ran and which remain pending; do not describe the contribution as fully validated. For the internal limitation route, verify the reproducer against your documented support contract and save its expected failure or documented fallback. A limitation report needs accurate reproduced evidence; it does not require a speculative fix or a test that falsely passes.

  4. Verify and save

    10 min

    Save focused validation logs, exact reproduction commands, environment details, and any untested path. Keep the contribution local.

What to save

Reproducible behavior and precise before/after or limitation evidence.

Watch for: Adding a broad test suite run as a substitute for checking the exact behavior being fixed.
