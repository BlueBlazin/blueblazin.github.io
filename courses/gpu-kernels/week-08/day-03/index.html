Build a Minimal Reproducer and Focused Fix

By the end of this hour

  • Build the smallest executable reproducer for a real observed behavior.
  • Make one focused code, test or instruction correction; use an internal limitation case if no legitimate upstream defect exists.

Before you begin

  • One previously observed upstream issue, documentation defect, or benchmark inconsistency; if none was found, choose one actual limitation in your own repository.
  • The relevant upstream source and contribution guidance.

Environment or workflow question? Day 0 handbook.

The key idea

An upstream contribution should solve a specific observed problem and make its effect easy to review. A small regression test, documentation correction, or benchmark-methodology fix can be more useful than a broad performance rewrite. Begin with a reproducer that distinguishes expected from actual behavior, then make the minimum change needed. Follow the project's conventions and avoid claiming support beyond the tested environment. This session produces a local review-ready draft; opening an issue, posting a comment, or submitting a pull request is a separate user-directed action. If no legitimate upstream defect was found, use this hour to produce an internal regression case or limitation analysis for a real behavior in your own kernel repository. That is an accepted course artifact, clearly labeled internal.

Your 60-minute plan

  1. Retrieve

    5 min

    Describe the observed issue, who it affects, and the smallest input that demonstrates it.

  2. Study

    10 min

    Use the core resources above for ten minutes in total, focusing only on the indicated sections. Read the target project’s contribution and test instructions for the affected area; inspect an adjacent existing example.

  3. Build

    35 min

    Choose one behavior actually observed in your kernel work. Reduce it to the smallest shape, dtype, layout and input that demonstrates the difference between expected and actual output or timing. Record the relevant source revision. If it is a genuine defect, prepare the smallest code or test change that addresses it; if it is an intentional support limit, write an executable rejection/fallback check instead. Use a real upstream candidate only when one already exists; otherwise work in your own repository. Exclude unrelated formatting, upgrades and speculative optimization. Save the focused diff and reproducer; publication and portfolio packaging belong to the shared Day0 guide.

  4. Verify and save

    10 min

    Save the focused diff or correction draft, minimal reproducer, and a concise statement of why the change is needed.

What to save

Smallest reproducer plus a focused diff or documented limitation check.

Watch for: Inventing an upstream issue simply to have a contribution in the portfolio.

Check your understanding

What makes a small documentation correction technically valuable?

Check your reasoning

It prevents a demonstrated setup or usage failure and is supported by a precise reproducer or verifiable corrected instruction.
