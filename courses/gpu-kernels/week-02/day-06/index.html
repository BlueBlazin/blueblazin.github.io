Hour 1 of 2 · 60 minutes

Implement Triton RMSNorm Forward

By the end of this hour

  • Implement a fused Triton RMSNorm forward pass.
  • Mask padding while dividing the reduction by the actual row width.

Before you begin

  • The RMSNorm reference and precision contract from 4-1.
  • The Triton softmax row-addressing pattern.

Environment or workflow question? Day 0 handbook.

The key idea

RMSNorm uses a row reduction like softmax, but padded lanes have a different neutral value. Loading invalid input lanes as zero lets their squared values contribute nothing to the sum. The denominator is the actual width N, not the padded power-of-two block size. After computing the FP32 inverse root-mean-square, each lane multiplies its input by that scalar and its corresponding weight. A single program can keep these intermediate values local and store one output row. Weight broadcasting, row stride, and output casting need explicit attention even when the central formula is only a few operations.

Your 60-minute plan

  1. Retrieve

    5 min

    For width 33 padded to 64 lanes, which number divides the sum of squares, and why?

  2. Study

    10 min

    Use the core resources above for ten minutes in total, focusing only on the indicated sections. Review K3’s normalization load/reduce/store pattern and locate where it converts to FP32. Map each line to your own RMSNorm formula.

  3. Build

    35 min

    Create kernels/triton_rmsnorm.py using one program per row. Load input lanes under c < N with zero padding, cast to FP32, sum squares, divide by N, add the fixed epsilon, and take reciprocal square root. Load the length-N weight with the same tail mask and apply it before the deliberate output cast. Validate your wrapper’s device, dtype, shape, and contiguity checks. Start with row counts 1 and 4 and widths 8, 32, and 128, using both unit and varying weights. Compare full outputs with the saved reference.

  4. Verify and save

    10 min

    Save errors for each small shape and confirm non-unit weights are applied across every row. Preserve the reference and epsilon unchanged.

What to save

Forward outputs agree on small supported shapes.

Watch for: Dividing by the padded block width produces a systematic scale error on non-power-of-two rows.

Check your understanding

Why is zero the right padded value for this reduction but not for softmax’s maximum?

Check your reasoning

Zero contributes nothing to a sum of squares, whereas it could incorrectly replace a negative row maximum in softmax.

Validate RMSNorm Across Row Shapes

By the end of this hour

  • Exercise RMSNorm’s boundary widths and declared dtypes.
  • Report numerical error against an explicit accumulation reference.

Before you begin

  • Working Triton RMSNorm forward and its frozen shape matrix.
  • The FP32-accumulating reference from 4-1.

Environment or workflow question? Day 0 handbook.

The key idea

An error table is more useful than a single pass/fail label when reduction length and storage precision vary. Maximum absolute error captures large deviations; relative error becomes unstable near zero, so use it with a stated denominator convention or a mixed absolute/relative check. Test the actual dtype that the kernel accepts and compare with a reference that models its cast locations. A high-precision calculation can additionally reveal rounding behavior, but is not a substitute for exercising the GPU path. Zero, constant, and irregular rows reveal different mistakes in epsilon handling, division, weight broadcasting, and masking.

Your 60-minute plan

  1. Retrieve

    5 min

    Name one test that isolates epsilon behavior and another that isolates the padded-width divisor.

  2. Study

    10 min

    Use the core resources above for ten minutes in total, focusing only on the indicated sections. Revisit K3’s normalization validation patterns. Identify which calculations belong in FP32 and which outputs are intentionally rounded.

  3. Build

    35 min

    Run the frozen row-count/width matrix using random, zero, constant, and alternating-sign rows plus a varying weight vector. Add any lower-precision dtype explicitly declared in your contract, keeping FP32 accumulation in both reference and kernel. Save maximum absolute error and a carefully defined relative or mixed-tolerance result per case. Include a deliberately unsupported noncontiguous input to verify the wrapper rejects it. When a case fails, inspect the first failing row and its denominator before adjusting the support or tolerance; document any justified narrowing of the contract.

  4. Verify and save

    10 min

    Save reports/kernels/rmsnorm-errors.csv and summarize the largest error by dtype. Re-run the small baseline cases and ensure the final contract matches the wrapper.

What to save

Error table covers the declared support and precision contract.

Watch for: Do not claim BF16 or FP16 support because an FP32-only test passed.

Check your understanding

Why is relative error alone misleading for an output close to zero?

Check your reasoning

Dividing by a tiny reference value can produce a huge relative error for a negligible absolute difference; an absolute tolerance or stated mixed criterion is needed.
