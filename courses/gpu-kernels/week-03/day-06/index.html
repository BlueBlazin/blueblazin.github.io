Freeze Matmul Tuning and Baselines

By the end of this hour

  • Predeclare a small matmul tuning search and measurement matrix.
  • Prepare fair library and compiled-composition baselines.

Before you begin

  • The validated matmul kernel and exact support/precision contract.
  • Your reusable timing utility and saved GPU manifest.

Environment or workflow question? Day 0 handbook.

The key idea

Tuning changes resource use as well as arithmetic reuse. Larger output tiles can reuse input values across more dot products, but need larger accumulators and can reduce the number of active programs. More warps are not automatically better. A bounded search makes the experiment tractable and keeps the learner from chasing noise across hundreds of configurations. Baselines must use the same stored inputs, precision, shapes, and output semantics. Today you freeze the candidates and commands; the next lesson measures them. This separation makes it easier to report a disappointing result without changing the question afterward.

Your 60-minute plan

  1. Retrieve

    5 min

    Explain one benefit and one cost of doubling an output tile dimension.

  2. Study

    10 min

    Use the core resources above for ten minutes in total, focusing only on the indicated sections. Read K3’s matmul tuning parameters and K2’s occupancy discussion. Distinguish potential occupancy from a measurement of achieved occupancy.

  3. Build

    35 min

    Create configs/matmul-search.json with three or four known-valid tile configurations, varying one factor where practical. Choose four supported shapes covering square and rectangular products, all within the existing memory allowance. Freeze seeds, FP16 input/FP32 accumulation policy, warm-up count, repetition count, and three independent timing batches. Prepare torch.matmul and torch.compile of the corresponding matmul function as baselines; the fused composition will be added after the epilogue lesson. Run only a small correctness smoke test per candidate today. Write the expected reuse/resource trade-off beside each configuration and keep the list fixed. For the FP32 reference, explicitly select and record IEEE FP32 matmul behavior; converting inputs with .float() does not by itself disable TF32. If claiming FP32 accumulation for an FP16 torch.matmul baseline, disable reduced-precision FP16 reductions using the controls documented for the pinned PyTorch version.

  4. Verify and save

    10 min

    Check each candidate compiles and passes the smoke case. Save the manifest and a single command that will run the fixed search without interactive tuning.

What to save

Predeclared tiles, shapes, and baseline settings.

Watch for: Do not claim higher achieved occupancy merely because a configuration uses a smaller tile; measure it or describe it as a hypothesis.

Check your understanding

Why freeze the tile search before examining timings?

Check your reasoning

It bounds compute and reduces selection based on random timing noise or repeatedly changing the benchmark question.

Hour 2 of 2 · 60 minutes

Measure Tile Reuse and Occupancy

By the end of this hour

  • Measure the frozen tile search with repeated timing batches.
  • Explain observed performance using reuse and resource trade-offs.

Before you begin

  • The frozen matmul search manifest and executable benchmark command.
  • The validated candidates and resident input-generation routine.

Environment or workflow question? Day 0 handbook.

The key idea

The fastest tile can change with matrix shape because a configuration balances reuse, parallel work, and per-program resources. A wide tile that helps a large square product may waste lanes on a narrow output or leave too few independent programs. Timing variability also matters: a tiny median difference is weak evidence when the batch spreads overlap substantially. Preserve every candidate’s raw measurements rather than retaining only the winner. You can infer plausible resource trade-offs from tile dimensions, but hardware counters are needed for a direct occupancy claim. This lesson stays inside the predefined search.

Your 60-minute plan

  1. Retrieve

    5 min

    For each frozen configuration, predict which of your four shapes it should help or hurt and explain why.

  2. Study

    10 min

    Use the core resources above for ten minutes in total, focusing only on the indicated sections. Review K2’s occupancy/performance relationship and K3’s tile-reuse discussion. Choose two observations to compare with your predictions.

  3. Build

    35 min

    Run the fixed candidate-by-shape matrix sequentially on one GPU. Warm compilation, verify each output against the existing reference, then collect at least three independent timing batches with raw samples. Save median, spread, and any launch or validation failure without dropping rows. For one shape, inspect the best and worst valid configurations and compare their output-tile area, K chunk, program count, and obvious wasted tail lanes. If compiler resource metadata is readily available, record it; otherwise label register-pressure and occupancy explanations as hypotheses. Do not expand the search today.

  4. Verify and save

    10 min

    Save reports/kernels/matmul-search.csv and a short prediction-versus-observation note. Check that differences smaller than timing variability are described cautiously.

What to save

Tile timing table with median, variability, and reuse observations.

Watch for: Selecting the single smallest sample favors noise; compare repeated-batch summaries instead.

Check your understanding

Why might a tile with better reuse still run more slowly?

Check your reasoning

Its larger resource footprint can reduce parallel execution, or its shape can waste work and leave too few output programs.
