Measure RMSNorm Wins and Losses

By the end of this hour

  • Measure RMSNorm against eager and compiled implementations.
  • Explain how row count and width affect the result.

Before you begin

  • The passing RMSNorm support/error matrix.
  • Your synchronized timer and pinned GPU manifest.

Environment or workflow question? Day 0 handbook.

The key idea

RMSNorm fusion removes intermediate square, reduction, and scaling tensors, but resource use and launch overhead still determine performance. With many rows, independent row programs provide more parallel work. Very wide rows can increase register pressure; very narrow rows may do too little work per launch. The weight vector is shared across rows and can be cached, so a simplistic traffic count should be labeled as a model rather than a measurement. Baselines must implement the same epsilon, accumulation dtype, output dtype, and scaling order. A useful systems report explains where the custom kernel loses as well as wins.

Your 60-minute plan

  1. Retrieve

    5 min

    Predict the easiest and hardest shapes for your one-program-per-row kernel, then state a result that would contradict the prediction.

  2. Study

    10 min

    Use the core resources above for ten minutes in total, focusing only on the indicated sections. Use K3’s normalization performance discussion to identify row-parallelism and resource-pressure hypotheses. Keep the existing support contract fixed.

  3. Build

    35 min

    Choose six shapes already covered by correctness checks, spanning narrow/wide rows and few/many rows. Create eager and torch.compile versions of the identical FP32-accumulating RMSNorm expression. Warm each candidate, confirm outputs, and benchmark sequentially with resident inputs and matched allocation behavior. Save at least three independent batches, medians, and spread; log cold compilation separately. Add speedup ratios relative to both baselines, including values below one. Write a short explanation of one favorable and one unfavorable regime, identifying which explanations are hypotheses rather than directly measured hardware facts.

  4. Verify and save

    10 min

    Save reports/kernels/rmsnorm.md with the support contract, error table link, timing results, and environment command. Check that every advertised win names a shape and dtype.

What to save

Validated support matrix and timing table containing wins and losses.

Watch for: A different epsilon or accumulation dtype makes the baseline a different numerical operation.

Check your understanding

Why does an operator speedup not directly predict a decoder speedup?

Check your reasoning

The decoder spends only part of its time in that operator, and integration can change launches, fusion, and memory behavior; end-to-end measurement is still needed.
