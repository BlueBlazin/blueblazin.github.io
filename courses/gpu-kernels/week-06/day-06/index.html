Port One Row Kernel to Pallas

By the end of this hour

  • Port one existing row operation to the supported Pallas GPU model.
  • Demonstrate its smallest actual GPU case.

Before you begin

  • The annotated Pallas example from 11-2 and your softmax/RMSNorm reference.
  • Before this lab, follow the Day0 H100 readiness checkpoint and run the official smoke on the compatible rented device. Keep that setup bounded; shift the calendar if blocked.

Environment or workflow question? Day 0 handbook.

The key idea

Choose one familiar operation so this hour isolates the Pallas programming model. A restricted row RMSNorm or softmax requires a clear mapping of rows and features to the documented GPU execution model, correct reductions, and explicit handling of any padded lanes. Start with a shape that the official example and backend support directly. Avoid importing assumptions from Triton's program layout or another Pallas backend. The objective is one real H100 output matching JAX; broader shapes and dtypes are tomorrow's validation work, and speed is a later question.

  2. Study

    10 min

    Use the core resources above for ten minutes in total, focusing only on the indicated sections. Use K6 to locate the supported reduction and data-access patterns that correspond to your selected operation.

  3. Build

    35 min

    Choose either row RMSNorm or stable softmax and write a narrow contract with one dtype and one small compatible feature width. Build a Pallas kernel using the working Mosaic GPU skeleton, adapting only the data loads, arithmetic, reductions, and stores required by that operation. Keep the JAX reference in a separate function and use identical deterministic inputs. Run the smallest declared case on the H100, force completion, and compare output values and shape. If lowering fails, shrink to the last working operation and record the exact unsupported construct rather than changing backend silently.

  4. Verify and save

    10 min

    Save the kernel, contract, actual GPU device record, and small-case maximum error. Export the work and stop the rental when done.

What to save

Watch for: Assuming Triton-style reductions or launch semantics transfer unchanged to Pallas.

Validate the Pallas GPU Kernel

By the end of this hour

  • Validate the Pallas operation across its declared contract.
  • Make tails and unsupported cases explicit.

Before you begin

  • The small working H100 kernel and JAX reference from step 11-3.
  • A frozen list of intended supported shapes and dtypes.

Environment or workflow question? Day 0 handbook.

The key idea

Portability does not eliminate the need for a support contract. A row kernel may be correct for one width yet mishandle padded lanes, additional rows, or a second dtype. A validation matrix makes the boundary visible, including cases intentionally rejected. For normalization operations, extreme finite values, zeros, and repeated inputs can expose different errors than standard random inputs. Compare actual GPU results using the same quantized inputs and an explicit reference precision policy. Do not count interpretation-only tests as completion of this GPU lab, even when they agree perfectly.

Your 60-minute plan

  1. Retrieve

    5 min

    Name the most likely failure at the first feature width outside your initial supported case.

  2. Study

    10 min

    Use the core resources above for ten minutes in total, focusing only on the indicated sections. Revisit K6 constraints relevant to shapes, layouts, and reductions; remove unsupported ambitions from the contract.

  3. Build

    35 min

    Parameterize the reference comparison over your declared rows, feature widths, and dtypes, retaining a deliberately small matrix. Include zeros, repeated values, and finite large-magnitude inputs. Test a supported tail if the kernel claims one; otherwise add an explicit rejection example for a nonconforming width. Measure maximum absolute error and a norm-relative error after synchronizing actual H100 execution. Investigate failed cases by checking masks and reduction denominators before adjusting precision. If hardware execution remains blocked, preserve the incomplete status and use later flex time rather than substituting CPU interpretation. Choose large-magnitude cases within a declared range where the reference intermediates remain finite; finite inputs alone do not rule out overflow in a sum of squares.

  4. Verify and save

    10 min

    Save the complete support/error matrix, tested backend versions, and any blocker. Export evidence and reconcile the short H100 session with the ledger.

What to save

One actual Pallas GPU kernel agrees with JAX across its supported contract.

Watch for: Adding a dtype to the README because the reference supports it when the GPU kernel has not been tested.

Check your understanding

Can a single passing square or power-of-two case establish general shape support?

Check your reasoning

No. General support requires evidence for the declared boundaries and masking behavior, or a narrower explicit contract.
