Implement RMSNorm Weight Gradient Reduction

By the end of this hour

  • Implement the shared weight-gradient reduction.
  • Check gradients across row and feature boundaries.

Before you begin

  • A validated Triton dx kernel from step 9-2.
  • The formula ∂L/∂wj=∑igijxijri\partial L/\partial w_j=\sum_i g_{ij}x_{ij}r_i∂L/∂wj​=∑i​gij​xij​ri​.

Environment or workflow question? Day 0 handbook.

The key idea

Each output weight gradient combines contributions from every row, so independent row programs cannot simply store to the same dw locations. For a small supported shape family, a clear two-stage design writes row or row-group partials and then reduces them in a second kernel. This uses extra memory but makes ownership and correctness visible. Scratch buffers must have a bounded size and be fully written before being read. The first implementation need not beat a library backward; it must handle all declared dimensions without races or silently dropped rows.

Validate Actual GPU Gradient Dtypes

By the end of this hour

  • Validate the actual supported GPU gradient dtypes.
  • Separate derivative correctness from numerical error.

Before you begin

  • The working dx/dw kernels and saved FP64 algebra check.
  • A declared list of supported shapes, dtypes, and tolerances.

Environment or workflow question? Day 0 handbook.

The key idea

A high-precision derivative check validates mathematical expressions, not every low-precision implementation of them. GPU error can arise from input quantization, accumulation order, casts, tail masks, or incorrect strides. Compare the kernel to a reference fed the same already-quantized inputs, and report errors for dx and dw separately. Relative error alone is unstable near zero, so pair maximum absolute error with a norm-based relative measure and a stated elementwise criterion. Tolerances should reflect the operation and supported dtype; an arbitrary relaxed threshold can conceal a reduction bug.

Your 60-minute plan

  1. Retrieve

    5 min

    Explain why a passing FP64 CPU check does not certify a BF16 GPU backward.

  2. Study

    10 min

    Use the core resources above for ten minutes in total, focusing only on the indicated sections. Revisit K3 normalization validation and your support contract; write the exact reference input and accumulation policy.

  3. Build

    35 min

    Turn the existing gradient comparisons into a small parameterized matrix rather than adding random tests indefinitely. Cover every declared dtype, one short and one longer supported width, a supported tail, varied row counts, zeros, and finite large-magnitude inputs. Quantize x, w, and g before constructing the high-precision comparison reference so both paths receive identical values. Record maximum absolute error, norm-relative error, and pass/fail for dx and dw. Investigate any failed row through its saved input and reduction intermediates; do not widen a tolerance without a numerical explanation. Predeclare the tested magnitude range and check that the FP32 square/reduction and reference gradients remain finite. Finite stored inputs alone do not guarantee finite intermediates; classify overflow outside the numerical contract instead of hiding it with a larger tolerance.

  4. Verify and save

    10 min

    Export the GPU gradient table and the distinct FP64 derivative result. List unsupported cases and any remaining blocker explicitly.

What to save

Actual GPU input/weight gradient agreement across the declared dtype and shape contract.

Watch for: Treating an FP64 reference gradcheck as evidence that the Triton BF16 path ran.

Check your understanding

What does a norm-relative error measure avoid compared with per-element relative error?

Check your reasoning

It reduces the distortion from individual reference elements near zero, though absolute and elementwise checks still matter.
