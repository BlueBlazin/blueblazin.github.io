Benchmark Restricted Attention Forward Correctness

By the end of this hour

  • Measure validated attention-forward latency and peak allocated memory.
  • Compare dense attention and SDPA with explicit backend context.

Before you begin

  • The passing restricted Triton attention-forward support matrix.
  • Your timing utility, dense reference, and PyTorch SDPA baseline.

Environment or workflow question? Day 0 handbook.

The key idea

Attention benchmarking needs a named workload and numerical contract: forward-only, causal, no dropout, fixed head dimension, supported dtype, and resident Q/K/V. Dense attention materializes scores, while SDPA may select an optimized backend depending on hardware, inputs, and configuration. Record that context instead of assuming SDPA is the dense implementation. Peak allocated memory should be measured for each isolated candidate after warm-up, with inputs already resident and prior temporary outputs released. Report whether memory numbers include output tensors and framework allocations. Correctness remains the gate; an unresolved forward pass is not a valid speed result.

Your 60-minute plan

  1. Retrieve

    5 min

    State the difference between dense score materialization, your restricted tiled forward, and the SDPA interface.

  2. Study

    10 min

    Use the core resources above for ten minutes in total, focusing only on the indicated sections. Use K3’s attention benchmark structure and K4’s memory argument to separate measured peak allocation from theoretical score storage.

  3. Build

    35 min

    Select three or four supported lengths and validate Triton, dense attention, and SDPA against the same reference before timing. Freeze dropout at zero, causality on, dtype, scale, and head dimension. Warm each candidate and collect three independent timing batches sequentially. For memory, release prior outputs, synchronize, reset peak statistics, run one candidate, synchronize again, and record baseline plus incremental peak allocated bytes. Record the SDPA backend choice when observable or its selection settings otherwise. Save raw timings, errors, memory numbers, and cold compile cost. If correctness is unresolved, save the blocker and defer performance claims.

  4. Verify and save

    10 min

    Save reports/kernels/attention-forward.md with support limits, commands, errors, latency, and memory accounting. State explicitly that backward is unimplemented and optional.

What to save

Working restricted forward with correctness, latency, and memory results; backward remains optional.

Watch for: Do not leave outputs or temporary tensors from a previous candidate alive when attributing peak memory to the next candidate.

Check your understanding

Why can comparing your kernel only with dense attention exaggerate its practical advantage?

Check your reasoning

A real framework may already use an optimized SDPA backend that avoids dense score storage; that is an important additional baseline.
