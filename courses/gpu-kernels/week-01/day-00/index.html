Set up the independent kernel labBefore Day 1 / when setup is needed

Standalone setup, review, contingency, audit or packaging. Preserve as a common reference rather than a numbered technical day.

This course uses a supplied small causal decoder as an integration workload, so building a language model is not a prerequisite. Its framework reference contains embeddings, causal attention, an MLP, and RMSNorm; it runs on CPU or CUDA and exposes a normalization hook for your later kernel. Deterministic random weights and synthetic integer tokens are sufficient for correctness and performance experiments. They do not establish language-model quality. Keep the fixture revision, state dict, and inputs fixed so a later speed comparison measures an implementation change rather than a different workload.

  • Python, Git, a PyTorch CPU environment, and basic tensor/autograd familiarity.
  • Download fixtures/decoder.py from this course’s setup guide; CUDA is unnecessary today.
  1. Retrieve

    Write the shapes for multiplying an M by K matrix by a K by N matrix, and recall how backward supplies an upstream gradient.

  2. Study

    Read the setup guide and the fixture’s configuration, forward signature, reference RMSNorm, and dense causal-attention functions. Follow the fixture’s documented smoke command.

  3. Build

    Create folders fixtures/, kernels/, tests/, reports/kernels/, and notes/kernels/ in a new Git repository. Copy in the supplied fixture and run its documented CPU smoke with a tiny configuration, fixed seed, and short integer-token batch. Save its dimensions, finite-output result, and deterministic random state dict with a content hash. Trace one forward pass through attention, normalization, and the MLP, recording input/output shapes in notes/kernels/fixture.md. Locate the normalization hook and cache smoke without modifying them. If PyTorch setup blocks progress, record the exact error and use the guide’s CPU environment before attempting anything on MPS.

  4. Verify and save

    Repeat the same CPU forward pass with the saved state and inputs. Confirm finite matching logits and save the executed command and package version.

Reference checklist

  • The supplied fixture runs locally on CPU and produces finite logits.
  • The configuration, seed, state dict hash, and token input are recorded.
  • My notes name attention, normalization, and MLP tensor shapes.
Self-check

Do random weights make the fixture unsuitable for a kernel correctness test?

No. Numerical equivalence and workload timing can be tested on fixed synthetic inputs and weights; language quality and realistic production conclusions require additional evidence.

Review execution, reductions, and benchmark validityUse later · after the relevant labs

Standalone setup, review, contingency, audit or packaging. Preserve as a common reference rather than a numbered technical day.

A kernel result combines three separate claims: it computes the intended operation, it supports the advertised inputs, and its comparison measures equivalent work. A fast exact-multiple example proves little about tails or numerical stability. A correct reduction can still be benchmarked unfairly if output allocation, compilation, or synchronization differs. This review asks you to reconstruct the reasoning from memory and then inspect your own evidence. Resolve one specific gap; do not spend this hour collecting a new favorable timing table or expanding the supported shape range.

  • Completed Modules 1 and 2, including CUDA/Triton vector add, softmax, and RMSNorm.
  • Saved support matrices, raw timing batches, and environment manifests.
  1. Retrieve

    Without notes, draw threads and blocks and write stable softmax plus RMSNorm, naming the normalized axis.

  2. Study

    Compare your explanation with K2 measurement guidance and the K3 reduction tutorial. Highlight one mistaken or uncertain point.

  3. Build

    Create reports/kernels/review-2.md. Explain a width-33 row in a power-of-two tile: distinguish invalid softmax lanes from RMSNorm zero padding and identify the correct denominator. Select one advertised edge case from each operation and locate its saved correctness evidence. Inspect the timer boundaries and allocation behavior of one performance comparison. Recompute one median from raw samples. If a real gap is cheap to resolve locally, add the focused reference or wrapper check; otherwise record the exact next GPU check for flex time. End with two claims you can defend and one limitation.

  4. Verify and save

    Confirm the report links each claim to a test result or raw measurement and leaves unresolved GPU checks visibly incomplete.

Reference checklist

  • I explained tail masking and the distinct reduction identities correctly.
  • One reported timing summary is recomputed from raw samples.
  • An identified gap is fixed with evidence or recorded for bounded follow-up.
Self-check

Why must RMSNorm divide the squared-value sum by the actual width rather than the padded tile width?

The operation averages over real features. Including padded lanes in the count changes the normalization even when their loaded values are zero.

Review tiled matmul and online attentionUse later · after the relevant labs

Standalone setup, review, contingency, audit or packaging. Preserve as a common reference rather than a numbered technical day.

Tiling and online normalization solve related memory problems through different mechanisms. Matmul tiles reuse loaded values across output calculations; online attention carries a compact running maximum, denominator, and weighted sum instead of retaining every score. Both require exact accounting for dimensions and numerical conventions. A tutorial may support far more hardware, shapes, or features than your implementation. The review’s goal is to explain your own restricted kernel and show where the evidence ends, while making one boundary failure easy to reproduce if it remains.

  • Completed Modules 3 and 4: tiled matmul and restricted attention forward.
  • Your support contracts, online-softmax reference, and saved attention tests.
  1. Retrieve

    Write the shapes of one matmul tile and one attention score tile from memory, then state the online m, l, and accumulator updates.

  2. Study

    Use K4 to check the recurrence and K3 to check the tile addressing conventions used in your pinned implementation.

  3. Build

    In reports/kernels/review-4.md, trace one matmul output element across two K tiles with a tail. Work through an online-softmax merge where the second tile contains the new maximum, showing rescaling of both denominator and weighted sum. Pick a query/key diagonal tile and draw its absolute-position causal mask. Locate saved evidence for a sequence length just beyond a block boundary and a future-key perturbation. Compare advertised shapes/dtypes with actual tests. Fix one documentation mismatch or write a minimal failing input for flex time; no additional tuning campaign is required.

  4. Verify and save

    Verify the manual recurrence against your local reference and record which results concern the PyTorch prototype versus the actual GPU kernel.

Reference checklist

  • The tile derivation shows address reuse and an explicit tail.
  • The merge rescales both old normalization and weighted state.
  • Causal and shape-support claims point to the correct implementation’s tests.
Self-check

Does a blockwise Python attention prototype prove your Triton implementation uses less peak GPU memory?

No. It demonstrates an algorithmic storage pattern. GPU peak-memory claims require measurements or a valid implementation-specific allocation analysis.

Explain Pallas Timing and StagingUse later · after the relevant labs

Standalone setup, review, contingency, audit or packaging. Preserve as a common reference rather than a numbered technical day.

A benchmark table is only interpretable when its timing boundary is clear. Compilation, allocation, transfer, enqueueing, and completed GPU work are different costs, and mixing them can create a fictitious advantage. Review correctness alongside timing because a fast incomplete or numerically wrong operation is not a useful result. The pipeline walkthrough provides a mechanism for explaining possible overlap, not proof that your row kernel uses the same mechanism. Keep explanations proportional to the evidence: distinguish a measured bottleneck, a supported inference, and an untested hypothesis.

  • Raw Pallas/JAX timing batches from step 12-1.
  • The Hopper pipeline trace and modern-attention comparison notes.
  1. Retrieve

    Name the synchronization point and resident-input policy used in your saved Pallas benchmark.

  2. Study

    Revisit the K6 benchmark and pipeline examples, checking that your terminology matches the actual operations.

  3. Build

    Audit the benchmark script line by line around timers and warmup. Confirm both outputs are synchronized, the same work is performed, and compilation is not leaking into the warmed batches. Recompute summary statistics from saved raw data. Rerun only a specific suspect case if the audit finds a real error and the H100 allowance permits it. Add a short staged-memory explanation based on your pipeline table, then separately interpret the row-kernel result using its own implementation and measured evidence. Retain slowdowns and document any uncertainty that the current data cannot resolve.

  4. Verify and save

    Finalize the timing/error table, methodology, pipeline diagram or table, and a short limitations paragraph without adding unneeded cloud runs.

Reference checklist

  • The timing audit confirms completion and matched measurement boundaries.
  • Summary numbers are regenerated from saved batches.
  • The explanation separates row-kernel evidence from the matmul walkthrough.
Self-check

Does understanding a pipelined matmul prove that your row kernel overlaps transfer and compute?

No. That claim requires evidence from the row kernel’s actual implementation and execution behavior.

Review differentiation, integration, and Pallas evidenceUse later · after the relevant labs

Standalone setup, review, contingency, audit or packaging. Preserve as a common reference rather than a numbered technical day.

Derivative algebra, actual GPU gradients, framework composition, and whole-model behavior are distinct checks. Passing an FP64 CPU gradcheck does not by itself validate a lower-precision GPU backward. Similarly, a Pallas interpreter run does not establish H100 execution. A useful review keeps these evidence levels separate and explains how unsupported shapes are handled before launch. The Pallas comparison should hold hardware, dtype, inputs, and completion boundaries constant; its compile time belongs in a separate result from steady-state execution.

  • Completed Modules 5 and 6, or a clearly recorded H100 setup blocker.
  • RMSNorm dx/dw tests, decoder parity results, and Pallas/JAX timing logs.
  1. Retrieve

    Derive the dimensions of dx and dw for M rows sharing one length-D RMSNorm weight vector.

  2. Study

    Check the K5 integration guidance for your pinned version and the K6 synchronization pattern used by your actual Pallas example.

  3. Build

    Create reports/kernels/review-6.md. Re-derive RMSNorm dx and dw without copying code, then compare with the saved CPU derivation. Link one actual supported-dtype GPU gradient result and the model-level parity smoke. Exercise or locate evidence for one unsupported input taking its declared fallback/rejection branch. Audit the Pallas result’s device identity and block_until_ready boundary, and recompute one warmed summary from raw logs. If H100 execution is still blocked, label that competency incomplete and reserve a specific flex task rather than substituting interpretation evidence.

  4. Verify and save

    Save the evidence ladder and a maximum three-item remediation list ordered by impact. Avoid rerunning checks already sufficiently supported.

Reference checklist

  • My derivation uses a feature reduction for dx and row reduction for dw.
  • The registered operator has supported and unsupported branch evidence.
  • Pallas hardware execution and compile/steady-state claims are accurately labeled.
Self-check

Why can a mathematically correct backward still fail when registered with autograd?

The registration may save the wrong tensors, return gradients in the wrong argument positions, or violate shape, dtype, mutation, or composition expectations.

Standalone setup, review, contingency, audit or packaging. Preserve as a common reference rather than a numbered technical day.

A reproduction fix should address an observed failure, such as an omitted dependency, ambiguous working directory, or missing configuration file. Changing the numerical algorithm or benchmark workload at the same time makes it harder to identify why results changed. Keep setup instructions explicit about supported hardware and where commands run. A compact smoke test gives quick feedback before expensive measurements, but it should exercise the actual custom-kernel path rather than an unnoticed fallback. If a dependency must change, record the reason and treat the resulting environment as a disclosed revision.

  • The clean-environment attempt and defect list from step 14-2.
  • A frozen benchmark manifest and smallest correctness smoke case.
  1. Retrieve

    Choose the first defect from the saved reproduction log and state the minimal change that would resolve it.

  2. Study

    Read the relevant official dependency or build guidance for that defect; avoid reviewing unrelated tooling.

  3. Build

    Apply the smallest fixes needed for the recorded setup failures: pin a missing dependency, correct a relative path, include a required configuration, or document an environment requirement. Update a setup script or README command sequence so it can be run from the clean checkout. Rerun only the correctness smoke and verify it selects the custom kernel on a supported input. Preserve the original experiment shapes, precision, warmup, and timing settings. If a required package revision changes, save both manifests and explain the compatibility reason rather than silently replacing the original environment record.

  4. Verify and save

Resolve Identified Benchmark Noise GapsUse later · after the relevant labs

Standalone setup, review, contingency, audit or packaging. Preserve as a common reference rather than a numbered technical day.

Repeated measurements are useful when they address a concrete uncertainty, such as whether a small apparent gain survives normal run-to-run variation. Keep the workload and baseline fixed while collecting the planned batches. Alternating variant order can reduce systematic order effects, but it does not make a shared or thermally variable machine perfectly controlled. Preserve raw samples and environmental notes instead of collapsing everything into a best number. If the remaining spread is large compared with the effect, an inconclusive result is more accurate than a confident speedup claim.

  • The prioritized risk register from step 15-1.
  • The exact saved benchmark manifests and supported hardware access.
  1. Retrieve

    State the decision criterion for the highest-priority rerun without looking at new timings.

  2. Study

    Read K2 timing considerations relevant to the flagged source of noise, and inspect the original batch structure.

  3. Build

    Execute only the reruns named in the risk register, starting with those that could invalidate the main conclusion. Collect the predeclared number of repeated batches, alternating variant order where appropriate, and retain all samples.   • All repeated batches and relevant machine observations are retained.
  • Each risk is resolved, bounded, or explicitly inconclusive.

Complete Shape Support and Precision MatrixUse later · after the relevant labs

Standalone setup, review, contingency, audit or packaging. Preserve as a common reference rather than a numbered technical day.

A support matrix is a public promise about which inputs the implementation handles. It should identify operation, device, shape family, layout, input/output dtype, accumulation dtype, and tolerance or error summary. Unsupported inputs, supported-but-failing cases, and untested cases are different categories; merging them into a blank cell conceals useful information. For differentiable kernels, forward and both relevant gradients need separate evidence. Complete only the advertised contract. Adding new shapes during the final audit creates new obligations and is unnecessary for a credible systems portfolio.

  • The kernel contracts and saved correctness results.
  • The remaining targeted correctness gaps from step 15-1.
  1. Retrieve

    Explain the difference between unsupported, untested, and failing supported inputs.

  2. Study

    Revisit the K3 numerical-validation examples and your operation-specific tolerance rationale.

  3. Build

    Build one compact table joining every advertised operation and supported dtype/layout/shape family to its existing correctness evidence. Mark missing entries explicitly, then run only the focused checks necessary to fill the declared contract. Include forward error and, where applicable, dx and dw errors separately. Add examples demonstrating rejection or documented fallback outside the contract. Preserve distinct tolerances for reductions, matmul, attention, and gradients rather than imposing one global BF16 threshold. If a supported case still fails, narrow the documented contract or leave the failure visible with a reproducer; do not mark it passed.

    Save the complete support/error matrix and links to the underlying result files. Confirm the README matches the tested contract exactly.

Reference checklist

  • Every advertised support entry points to correctness evidence.
  • Forward, input-gradient, and weight-gradient results remain distinguishable.
  • Unsupported, untested, and failed cases use explicit labels.
Self-check

Why is one universal BF16 tolerance unsuitable for every kernel?

Error depends on the operation, reduction length, accumulation policy, input scale, and output conditioning, not only the storage dtype.
