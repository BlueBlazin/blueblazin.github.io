Implement Triton Vector Addition Masks

By the end of this hour

  • Express vector addition using Triton program IDs and vector offsets.
  • Mask every out-of-range load and store.

Before you begin

  • The CUDA test matrix and PyTorch reference from 2-2.
  • The pinned Triton installation on the NVIDIA environment.

Environment or workflow question? Day 0 handbook.

The key idea

A Triton program works on a block of logical elements expressed as a vector of offsets. For block width B, offsets are program_id times B plus arange(0, B). A Boolean mask offsets < N describes the valid lanes of the final program. Masked loads supply a chosen value for invalid lanes, and masked stores prevent invalid writes. This resembles the CUDA coverage calculation but leaves more instruction scheduling to the compiler. Reusing the same inputs and reference makes the comparison about implementation, rather than accidental differences between two separately written test suites.

It supplies a value for invalid load lanes. The store still needs its own mask to avoid writing outside the output.

Compare Both Vector Addition Implementations

By the end of this hour

  • Compare CUDA, Triton, and PyTorch under one measurement protocol.
  • Explain launch-dominated and traffic-dominated vector addition.

Before you begin

  • Both passing vector-add implementations and the common test matrix.
  • Your synchronized timing utility and environment manifest.

Environment or workflow question? Day 0 handbook.

The key idea

Vector addition reads two arrays and writes one. For N FP32 elements, the simple payload estimate is 12N bytes, ignoring cache effects and any extra framework behavior. Dividing that estimate by elapsed time gives an effective bandwidth, not a direct hardware counter. Tiny vectors often expose launch and wrapper overhead; larger vectors provide more work per launch. A fair comparison fixes shapes, dtype, device residency, and whether allocation is included. Warmed custom kernels should not be compared against a first-call library baseline. Keep compilation costs in their own column and retain slower results.

  2. Study

  3. Build

Benchmark CUDA, Triton, and PyTorch sequentially with resident inputs, warm-up, and at least three independent timing batches. Match output-allocation semantics across wrappers or explicitly report the difference. Save raw samples, median, spread, setup cost, and the 12N/time payload bandwidth estimate. Write two paragraphs explaining the size-dependent ranking and whether the data support a launch-overhead or memory-traffic explanation.

  4. Verify and save

    10 min

    Check that all candidates used identical inputs and timing boundaries. Save reports/kernels/vector-add.md with the correctness matrix, timing table, and limitations.

What to save

Both kernels pass; timing table separates compilation and steady-state execution.

Watch for: Do not compare an allocating PyTorch expression with an allocation-free custom launch without disclosing that distinction.

Check your understanding

Can effective payload bandwidth exceed the GPU’s external-memory bandwidth?

Check your reasoning

It can when the simplified byte model counts data served from cache or omits relevant timing/context details; it is not a direct DRAM-bandwidth measurement.
