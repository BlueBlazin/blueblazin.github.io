Build Reliable GPU Timing Utilities

By the end of this hour

  • Measure asynchronous CUDA work with an explicit completion boundary.
  • Separate cold setup from repeated steady-state execution.

Before you begin

  • Use the Day0 NVIDIA readiness checklist immediately before this lab: pinned environment, successful GPU smoke and an explicit shutdown plan. If it is blocked, resolve the setup using the same study budget before continuing.
  • One small operation and the fixed decoder batch to time.

Environment or workflow question? Day 0 handbook.

The key idea

CUDA operations normally return control to Python before device work finishes. A wall-clock interval around the launch can therefore measure submission overhead rather than execution. A synchronized wall-clock measurement waits before the interval and after its last operation. CUDA events instead measure elapsed work on the relevant device stream when used correctly. Compilation, allocator setup, and cache warm-up make initial calls different from steady-state calls. Keep those costs visible in separate fields. Repeated timing batches reveal variability; a single impressively short number can be a synchronization mistake rather than an optimization.

Your 60-minute plan

  1. Retrieve

    5 min

    Sketch the timeline of Python launching a kernel while the GPU is still working. Mark where an unsynchronized timer stops.

  2. Study

    10 min

    Use the core resources above for ten minutes in total, focusing only on the indicated sections. Read K2 timing guidance, focusing on synchronization and CUDA events. Identify the event ordering needed to measure one stream.

  3. Build

    35 min

    Create kernels/benchmark.py with an untimed warm-up, a configurable repetition count, and at least three independent timing batches. Use resident tensors, synchronize before and after each wall-clock batch, and divide elapsed batch time by its call count. Return raw batch samples, their median, and spread. Add a separate cold-call measurement. Run a deliberately unsynchronized timer on the same operation, then the valid timer. Store both results with a timeline explanation. Keep host-to-device copies outside the steady-state region and retain an optional separate transfer measurement.

  4. Verify and save

    10 min

    Confirm repeated valid measurements are plausible, raw samples are saved, and the incorrect timer is labeled. Re-run once with a larger repetition count and explain any change.

What to save

Timing utility and explained discrepancy between valid and invalid measurements.

Watch for: Timing each candidate while another benchmark is using the same GPU invalidates the comparison.

Check your understanding

Why synchronize before starting the clock as well as after finishing?

Check your reasoning

The first synchronization excludes outstanding earlier work; the second ensures the measured work has actually completed.
