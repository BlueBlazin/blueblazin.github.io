Prepare a Small Upstream Contribution

By the end of this hour

  • Select a contribution supported by direct implementation experience.
  • Reduce the problem to a maintainable test or documentation change.

Before you begin

  • Your implementation notes and recorded friction from the course, including resolved problems or supported limitations.
  • A relevant framework or model repository and its contribution instructions.

Environment or workflow question? Day 0 handbook.

The key idea

Useful upstream work often begins with a narrow problem you can reproduce: an unclear tensor convention, a missing boundary-case test or an example whose instructions no longer run. Choose something supported by your own course work and read the existing issue discussion before editing. A contribution draft is a valid course outcome; acceptance is outside your control. Avoid making a broad feature request in place of evidence. The strongest small proposal explains observed behavior, expected behavior and the minimum change that connects them. If no current upstream issue remains, record the fixed version or supported limitation and publish a useful local compatibility note with a minimal example. Do not invent a defect or expand this into an open-ended search.

Resources for this hour

Your 60-minute plan

  1. Select one problem

    5 min

    Choose one actual friction from your PyTorch/JAX parity, cache implementation or weight-conversion work. Prefer a documentation or small test improvement that fits this hour.

  2. Check project context

    10 min

    Use the core resources above for ten minutes in total, focusing only on the indicated sections. Read the target repository contribution guide and search for an existing issue or fix. Record the repository revision and whether the behavior is still reproducible.

  3. Build the contribution draft

    35 min

    Create a minimal example or documentation correction separate from your full project. Include shapes, dtype, exact versions, expected behavior and observed result. Draft a concise issue or patch with a test when the change affects behavior. If an existing issue already covers it, prepare a small reproducer or evidence comment instead of a duplicate. If the issue is resolved or expected behavior, save a verified local compatibility note and runnable example instead; identify the relevant revision and avoid labeling it an upstream bug.

  4. Review scope

    10 min

    Save contributions/architecture-draft.md and any minimal patch. Remove unsupported claims, large unrelated changes and private data. Note the next human review or submission step without claiming the draft has been accepted.

What to save

A minimal reproducer and contribution draft, or a versioned compatibility/limitation note with runnable evidence.

Watch for: Do not promise a merge or expand a small reproducibility problem into a new model implementation.

Check your understanding

What is a successful outcome if the upstream project already fixed your issue?

Check your reasoning

Record the version and fix, verify a minimal example, and update your local compatibility note. A useful reproducible no-issue finding completes this hour; do not create a duplicate or invent another problem.
