Integrate And Validate LoRA Adapters

By the end of this hour

  • Attach tested adapters to explicitly selected pretrained linear layers.
  • Verify frozen weights, trainable counts and full-model merge equivalence.

Before you begin

  • The pinned pretrained baseline and tested LoRA wrapper.
  • A list of actual linear-module names from the loaded model.

Environment or workflow question? Day 0 handbook.

The key idea

An adapter experiment is defined partly by where adaptation is allowed. Selecting named projection layers makes the intervention reproducible and permits an exact trainable-parameter calculation. Freezing must be checked by both requires_grad settings and observed gradients after backward. Layer-level merge parity is necessary but insufficient: replacement logic, tied modules or an unintended target can still alter the full model. Compare complete model logits before training and after a small adapter change, keeping token IDs and evaluation settings fixed throughout.

Your 60-minute plan

  1. Retrieve

    5 min

    Explain how to compute the total adapter count when targeted projections have different input and output widths.

  2. Study

    10 min

    Use the core resources above for ten minutes in total, focusing only on the indicated sections. Review A5’s adaptation targets and inspect A6’s actual module structure. Choose a small explicit set, such as query and value projections, based on real names.

  3. Build

    35 min

    Enumerate the loaded model’s linear modules and record the exact target names, rank, alpha and adapter dropout choice. Replace only those targets with your tested wrapper; do not guess names from another architecture. Freeze every base parameter and construct the optimizer from adapter parameters only. Compare initial full logits with the saved baseline, then save the pristine adapter state before running one small backward/update on a short synthetic batch. Check all base gradients remain absent and sum trainable counts from the target shapes. Merge a separate evaluation copy and compare its logits with the unmerged adapted model. After these smoke checks, restore the pristine zero-update adapter state and create a fresh optimizer so the later SFT experiment does not inherit this synthetic update.

  4. Verify and save

    10 min

    Save the target manifest, freeze audit, trainable count and full-model merge error. Keep the smoke-test checkpoint separate from the pristine initialization; verify restored initial logits again match the pinned base.

What to save

Base stays frozen; trainable count and merge-logit equivalence pass.

Watch for: A broad name substring can wrap unintended modules; inspect and save the exact matched target list.

Check your understanding

Why should a merge-parity test use nonzero trained or manually perturbed adapter weights?

Check your reasoning

A zero-update adapter makes both paths equal even if merge logic is incomplete. A nonzero update exercises the actual addition and branch-disabling behavior.

Generate And Check Structured Data

By the end of this hour

  • Generate a small structured-extraction dataset with explicit family separation.
  • Check labels manually and freeze the train/validation/held-out manifest.

Before you begin

  • The pinned pretrained model and validated adapters.
  • A chosen short extraction schema that is easy to grade exactly.

Environment or workflow question? Day 0 handbook.

The key idea

A synthetic task is useful because its labels and failure conditions can be specified precisely. It can also be deceptively easy: repeated templates or entity patterns across splits allow memorization rather than transfer. Split generator template families and entity families before generating examples, then freeze the generated files. This course uses 300 training, 50 validation and 100 held-out examples. The held-out set is a development holdout that you authored, not an independent blind benchmark; keep that limitation visible when reporting results.

Your 60-minute plan

  1. Retrieve

    5 min

    Describe a leakage path that remains even when no complete text string is duplicated across splits.

  2. Study

    10 min

    Use the core resources above for ten minutes in total, focusing only on the indicated sections. Review the course SFT standard and A6’s context/tokenizer constraints. Choose one output schema, such as {"item": string, "quantity": integer}.

  3. Build

    35 min

    Write a deterministic generator for short order-like statements and exact JSON targets using a compact schema. Define separate template families and entity vocabularies for train, validation and held-out partitions before drawing examples. Generate exactly 300/50/100 rows with stable IDs, source-family labels and a seed. Check duplicate inputs and cross-split family overlap programmatically. Manually inspect at least five examples per split for unambiguous inputs, correct types and exact labels. Save a fixed prompt format and prevent later generation from silently overwriting the frozen files.

  4. Verify and save

    10 min

    Save data files, checksums, generator configuration and the manual-review notes. Document which aspects of the synthetic distribution will remain shared across splits.

What to save

Split manifest and checked labels document family separation.

Watch for: Do not generate the held-out set repeatedly until the pretrained model happens to perform well on it.

Check your understanding

Why does separating template families provide a stronger test than randomly splitting generated rows?

Check your reasoning

A random split can repeat the same sentence pattern in every partition. Family separation asks the model to apply the task to a different phrasing pattern, though it still does not establish broad real-world generalization.
