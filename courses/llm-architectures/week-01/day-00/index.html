Prepare a Reproducible Architecture WorkspaceBefore Day 1 / when setup is needed

Setup or refresher material belongs in optional readiness before Day1; keep it available but do not allocate a regular course day.

The course starts with small CPU examples because they make correctness checks inexpensive and avoid accelerator differences while you recover fluency. PyTorch and JAX need not share one environment if their package requirements conflict. Record the environments you actually create and verify simple computations in each; an installation command alone is not evidence that the setup works. Keep datasets, checkpoints and credentials outside committed source files. Cloud accelerators come later, after a measured workload justifies the cost.

  • Your M1 Max MacBook, a terminal and Git.
  • Python and your preferred virtual-environment manager.
  1. Orient

    Create an llm-architectures repository and read the course outcomes. Write the weekly study limit in README.md: five one-hour sessions, two hours Saturday, Sunday off.

  2. Prepare environments

    Create isolated Python environments with NumPy, PyTorch, JAX CPU support and a test runner. Follow current official installation instructions from the course setup guide; record the commands and versions that succeed.

  3. Build a smoke test

    Create model/, tests/, data/, notes/ and experiments/. In each framework, multiply fixed 2×3 and 3×2 matrices, compare against NumPy and differentiate a sum-of-squares loss with respect to the first matrix. Save the expected result and a runnable smoke script. Keep package metadata or lock files with the code, and ignore generated data and large checkpoints.

  4. Verify and save

    Open a fresh terminal, activate each documented environment and rerun the script. Save notes/environment.md with Python, package, OS and device details, then commit the small scaffold.

Reference checklist

  • Both frameworks reproduce the fixed NumPy matrix result.
  • A fresh terminal can run the documented CPU smoke checks.
  • Environment versions, setup commands and repository exclusions are saved.
Self-check

It narrows the initial problem to mathematical and layout correctness. Later device and precision changes can then be evaluated against an established reference.

Build Your Tensor Debugging ToolkitBefore Day 1 / when setup is needed

Setup or refresher material belongs in optional readiness before Day1; keep it available but do not allocate a regular course day.

Many model bugs preserve plausible shapes. A vector can broadcast along the wrong axis, a transpose can silently change meaning, or a test can compare two versions of the same mistake. Start with hand-checkable arrays and independently organized references. Absolute error measures a raw difference; relative error needs care near zero. Choose tolerances for the dtype and operation under test, and include an exact tiny example where possible. These habits will carry through attention, parameter conversion, cache tests and training experiments.

  • The working CPU environments and repository from the first session.
  • A test runner or a simple script that exits with an error on failed assertions.
  1. Recall

    Write the shapes of x:[2,3] plus b:[3], and x transposed. Predict which axis receives the bias before executing code.

  2. Inspect the testing pattern

    Create a short note distinguishing shape assertions, exact small-array examples, reference comparisons and behavioral invariants. Write one failure each type can catch.

  3. Build three checks

    Using fixed NumPy arrays, implement row-wise bias addition, a linear projection and a scalar weighted sum. Write independent expected values for at least one tiny case. Compare PyTorch outputs with NumPy, report maximum absolute error and choose a stated FP32 tolerance. Test a non-square shape so a mistaken transpose cannot hide. Deliberately change an axis or transpose once and verify a test fails, then restore the correct code.

  4. Save the debugging template

    Save tests/test_tensor_contracts.py and notes/testing.md with fixture, shape, dtype, reference, tolerance and failure-message conventions. Rerun the tests from the documented command.

Reference checklist

  • Three operations have value checks as well as shape checks.
  • A deliberate layout or axis mistake produces a failing test.
  • The fixture, dtype, tolerance and runnable command are documented.
Self-check

Why is a non-square fixture often more revealing than a square one?

Swapping two unequal dimensions often creates a visible mismatch, while a square tensor can preserve the same shape after an incorrect transpose. Value checks remain necessary in both cases.

Diagnose Essential Model Engineering KnowledgeBefore Day 1 / when setup is needed

Setup or refresher material belongs in optional readiness before Day1; keep it available but do not allocate a regular course day.

The diagnostic is a map of what to refresh, not an entrance exam. Decoder implementation combines tensor algebra, differentiation, numerical stability and experimental discipline. A program can have correct output dimensions while using the wrong normalization axis or leaking future tokens. A plausible answer is less useful than a reasoned one: write dimensions, assumptions and a counterexample where possible. Mark uncertain answers explicitly. Revisit gaps while implementing the relevant component or during scheduled flex time instead of extending this hour into an unplanned prerequisite course.

  • A blank notes file and a Python environment; no GPU is needed.
  1. Retrieve

    Without references, write what Q, K and V represent and why a decoder cannot attend to a future token.

  2. Study

    Spend ten minutes answering the five questions below before opening the answer panel. Use A1 only afterward to locate one relevant refresh topic.

  3. Build

    Create notes/diagnostic.md and answer: (1) For Q,K,V shaped [2,4,8,16], what are attention-score and output shapes? (2) How do you compute cross-entropy for logits [1000,999] with target 0 without overflow? (3) For L=(wx-y)^2, derive dL/dw. (4) Which attention entries must a causal mask exclude, and how would a future-token perturbation expose a reversed mask? (5) Why should documents be split into train and validation before creating overlapping token chunks? Record confidence and a small check for each answer, then rank your three highest-value gaps.

  4. Verify and save

    Compare with the answer panel, correct errors in a different paragraph, and save a three-item gap list with the later lab or flex session where each gap will be revisited.

Reference checklist

  • Five attempted answers are saved before corrections.
  • Each uncertain or incorrect answer has a concrete correction.
  • Three prioritized gaps have a planned follow-up.
Self-check

What are the diagnostic answers, and which one changed your reasoning?

1: scores [2,4,8,8], output [2,4,8,16]. 2: subtract 1000; loss = log(1+exp(-1)), about 0.3133. 3: 2(wx-y)x. 4: exclude key position j greater than query position i; changing later input tokens must leave earlier outputs unchanged. 5: otherwise overlapping or related text from one document may appear in both sets and inflate apparent generalization. Explain your largest correction in your own words.

Self-check

What should the three answers establish?

Scores have shape [B,H,T,T], head outputs [B,H,T,D], and concatenated heads [B,T,H*D]; perturbing later tokens must not change earlier outputs. Orthogonal rotations satisfy R_mᵀR_n=R_(n−m) within each paired subspace. A pure step receives and returns explicit state; random keys are split explicitly. Equal seeds in different frameworks do not promise identical random arrays, so transfer the actual parameter values and account for layout differences.

Self-check

What should the three answers establish?

The logical KV payload is 2*L*B*T*Hkv*d*s; allocation capacity and metadata are additional. Each cached path must match its own full-prefix logits with aligned positions and masks. With delta W=(alpha/r)*B*A, A:[r,d_in], B:[d_out,r], there are r*(d_in+d_out) trainable factors; initializing one factor to zero and the other nonzero gives a zero initial update without blocking every gradient. Masking prompt targets defines which outputs train the adapter; separated families reduce a specific source of leakage but do not establish broad real-world generalization.

A model card explains what an artifact is and what its evidence supports; a data card explains where its learning data came from and how it was transformed. Neither should be a marketing summary. For a small educational model, model size, training tokens, tokenizer, data distribution and evaluation scope strongly constrain interpretation. Use exact counts from saved artifacts rather than remembered numbers.   • The model checkpoint identifiers and reproduction command.

  2. Study

  3. Build

    Draft MODEL_CARD.md with architecture components, exact parameter count, tokenizer, training-token budget, optimizer/settings, intended educational use, evaluated tasks and limitations. Draft DATA_CARD.md with source and revision, license reference, selection/preprocessing, split construction, synthetic-task generation and known distribution limits.
