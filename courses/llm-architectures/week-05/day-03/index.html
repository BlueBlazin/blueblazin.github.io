Evaluate Structured Task Improvement Honestly

By the end of this hour

  • Compare before/after held-out validity and task accuracy fairly.
  • Report error categories and synthetic-data limitations honestly.

Before you begin

  • The selected adapter checkpoint, learning curves and frozen baseline outputs.
  • The unchanged 100-example held-out set and grader.

Environment or workflow question? Day 0 handbook.

The key idea

A fair before/after comparison holds the model revision, prompts, decoding cap, data and grader constant; the adapter is the intended changed variable. Report counts as well as percentages so the small evaluation size stays visible. Per-example paired changes show whether the adapter fixes baseline failures or introduces regressions. Because you generated the task and saw its design, this result supports a narrow claim about the specified synthetic distribution. It does not establish broad tool-use reliability, reasoning ability or robustness to arbitrary real-world inputs.

Your 60-minute plan

  1. Retrieve

    5 min

    State one claim this experiment can support and one attractive claim it cannot support.

  2. Study

    10 min

    Use the core resources above for ten minutes in total, focusing only on the indicated sections. Review the course reporting standard: changed variable, raw results, cost, confounds and limits. Keep the held-out protocol frozen.

  3. Build

    35 min

    Run the selected adapter once on the 100 held-out examples with the exact baseline decoding settings and grader. Save raw outputs, validity flags, correctness flags and a paired table beside the baseline. Report counts and rates for valid schema and correct task, then list improved, regressed and unchanged examples. Inspect a small sample of failures only after computing final metrics and classify malformed output, wrong field value, extra text or truncation. Write a concise result note linking the learning curve, trainable count, run cap and dataset-family design; do not retune from these final errors.

  4. Verify and save

    10 min

    Save the before/after table, final report and a command that reproduces a small evaluation subset. State whether the adapter improved the chosen task, including a negative result if that is what the data shows.

What to save

Before/after held-out metrics, learning curve and limitations recorded.

Watch for: Do not treat a handful of improved examples as stronger evidence than the complete frozen evaluation.

Check your understanding

Can higher JSON validity with unchanged task accuracy be called improved extraction?

Check your reasoning

It demonstrates better formatting under this protocol, but not improved extraction correctness. Report the two outcomes separately and avoid broadening the claim.
