Build A Dense Masked Reference

By the end of this hour

  • Construct an independently organized dense masked reference.
  • Compare output, input gradients, router gradients and expert gradients.

Before you begin

  • The explicit-loop MoE module from the previous session.
  • The frozen six-token fixture and design contract.

Environment or workflow question? Day 0 handbook.

The key idea

A dense masked reference evaluates every expert for every token, stacks the outputs, and masks all but the selected two. It is intentionally wasteful but mathematically comparable to sparse dispatch. Independent organization is valuable: reproducing the same indexing loop in both paths can reproduce the same bug. Gradient comparison must use identical parameters, inputs and scalar upstream weights. Stay away from tied router scores, where a tiny perturbation may change the discrete top-k selection and invalidate a smooth local comparison.

Your 60-minute plan

  1. Retrieve

    5 min

    Name the four gradient groups you must inspect: input, router, first expert matrix and second expert matrix.

  2. Study

    10 min

    Use the core resources above for ten minutes in total, focusing only on the indicated sections. Read your routing contract and write the dense formula with a [N,4] sparse weight matrix. No new reading is required.

  3. Build

    35 min

    Evaluate all four experts on the entire [N,D] input and stack outputs as [N,4,D]. Scatter the normalized top-2 weights into a zero [N,4] tensor, multiply and sum along the expert axis. Clone the model state and input for the two paths. Use the same fixed random tensor to form a scalar weighted output sum, then compare outputs and all available gradients in CPU FP32. Treat an unused expert’s absent gradient as zero only when interpreting the comparison, and deliberately swap two routing indices once to prove the test catches the error.

  4. Verify and save

    10 min

    Save a short parity table with maximum absolute errors and the test command. Restore the correct implementation after the deliberate failure.

What to save

MoE output and gradients match the reference.

Watch for: Router-score ties can make different top-k choices; use a fixture with comfortably separated scores for the parity test.

Check your understanding

Why is comparing only the output insufficient for a trainable MoE layer?

Check your reasoning

A detached gate or incorrect gradient path can preserve today’s forward output while preventing correct learning.

Inspect Routing And Validate Sparse Experts

By the end of this hour

  • Expose balanced and skewed expert utilization.
  • Explain what routing counts do and do not establish.

Before you begin

  • Passing MoE forward and gradient parity tests.
  • The parameter calculation in notes/moe-design.md.

Environment or workflow question? Day 0 handbook.

The key idea

Routing counts describe how often an expert is selected, not how useful it is. With N tokens and top-2 selection, the total count across four experts must be 2N when no token is dropped. Repeated inputs or a biased router may concentrate work on a few experts. That can create poor utilization even while forward and gradient parity remain perfect. This lab records the behavior rather than adding a balancing objective; changing training objectives would be a separate experiment with its own controls.

Your 60-minute plan

  1. Retrieve

    5 min

    Predict the total routing count for a batch of 24 tokens with top-2 routing and no dropping.

  2. Study

    10 min

    Use the core resources above for ten minutes in total, focusing only on the indicated sections. Review A7’s motivation for expert specialization and balanced utilization. Do not add its complete training machinery to the toy layer.

  3. Build

    35 min

    Add a small diagnostic that counts selected expert IDs and reports each count and fraction of the 2N assignments. Run a fixed random input batch, then a deliberately skewed fixture made from repeated inputs or a documented router-weight change. Save both count tables. Re-run the dense-reference parity checks on the skewed case. Extend notes/moe-design.md with your total and active parameter counts, two observations about utilization, and one reason the explicit implementation might run slower than a dense feed-forward layer despite activating fewer expert weights.

  4. Verify and save

    10 min

    Check counts sum to 2N in both fixtures. Save the report and test results; leave balancing losses and optimized dispatch in a clearly optional follow-up list.

What to save

Reference equality passes; skewed routing and parameter accounting are visible.

Watch for: A fast-looking tiny CPU timing is not evidence of production MoE throughput.

Check your understanding

Does a uniform routing histogram prove that the experts learned different useful functions?

Check your reasoning

No. It measures assignment frequency; specialization and usefulness require additional evidence.
