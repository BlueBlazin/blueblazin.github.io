Automate Tiny Training and Numerical Parity

By the end of this hour

  • Regenerate a small learning curve and cross-framework parity evidence.
  • Check new outputs rather than trusting historical artifacts.

Before you begin

  • The tiny training and CPU FP32 parity commands from the decoder labs.
  • The Day0 reproduction template; fill its inputs from the configurations, tokenizer/data manifests and environment records produced during the labs.

Environment or workflow question? Day 0 handbook.

The key idea

A reproduction smoke run verifies a narrow, affordable claim: the documented environment can train a tiny model briefly and reproduce the intended numerical relationships. It is not expected to recreate a long cloud experiment during one study hour. Use fresh output paths and a fixed tiny fixture. Compare logits, loss and selected gradients with tolerances appropriate to CPU FP32, and produce a learning curve with enough steps to show the pipeline actually updates parameters. Preserve failed results if they reveal a real portability problem.

Your 60-minute plan

  1. Retrieve

    5 min

    Recall the parity quantities established earlier: full logits, scalar loss and representative parameter gradients.

  2. Study

    10 min

    Use the core resources above for ten minutes in total, focusing only on the indicated sections. Read the documented acceptance criteria and tolerance choices before running; do not loosen them after seeing a failure without an explanation.

  3. Build

    35 min

    Create scripts/reproduce_architecture.py as a small orchestrator around the existing tiny training and PyTorch/JAX parity entry points. Accept an output directory, use the existing two-layer CPU fixture and write to a fresh directory. Record source commit, configuration, consumed-token loss history and parity errors. Propagate any failed required test rather than treating launched subprocesses as success. Run the script once from the environment specified by the Day0 reproduction template; verify that the curve/CSV and parity table were newly generated. Keep the long cloud experiment outside this command.

  4. Verify and save

    10 min

    Open the new curve and parity report. Confirm their metadata names the clean environment and current commit, then save the exact commands used.

What to save

An executable reproduction command writes fresh training/parity outputs with source and configuration metadata.

Watch for: A previously generated plot in the target directory can make a failed reproduction look successful; use fresh paths.

Check your understanding

Does this smoke run prove that the full long training experiment is exactly reproducible?

Check your reasoning

No. It verifies the small documented path; the full experiment needs its own inputs, hardware assumptions and run budget.

Hour 2 of 2 · 60 minutes

Test Reproduction Failure Handling

By the end of this hour

  • Provide one command that recreates the small architecture evidence.
  • Ensure failure produces a nonzero exit and a useful message.

Before you begin

  • The executable reproduction command from the previous retained hour.
  • A disposable output directory and copies of the small input manifest for failure injection.

Environment or workflow question? Day 0 handbook.

The key idea

A single reproduction entry point is an interface for a reviewer. It should validate required inputs, run the small training and parity tasks, write outputs to a chosen directory and fail clearly when a required check fails. It must not silently download huge assets or run the full training budget. A wrapper can reuse existing scripts; its value is removing ambiguity about order and settings. The final verification is to run that documented entry point in the clean environment and inspect only the outputs it just produced.

Resources for this hour

Read the indicated section, not the entire source. The core reading fits inside the plan below. A video is an alternative to reading, not extra homework.

  • Core · 10 min · documentation
    Python subprocess.run: check and timeout

    check, timeout and CalledProcessError: preserve child-process failure.

Your 60-minute plan

  1. Retrieve

    5 min

    List the minimal stages of your smoke run in order: validate inputs, train briefly, check parity and write the evidence summary.

  2. Study

    10 min

    Use the core resources above for ten minutes in total, focusing only on the indicated sections. Review the two working commands and their exit behavior. Confirm that a failed assertion is not swallowed by a broad exception handler.

  3. Build

    35 min

    Use copies of the small input manifest to test the reproduction command with a missing file and an invalid configuration; each must fail clearly with a nonzero exit. Force a parity subprocess failure and verify its status reaches the top-level command. Keep the valid source inputs untouched. Restore valid arguments, run the command into a new directory and confirm both tiny training and parity evidence are regenerated. Add only the input checks and failure propagation needed by these cases; use the Day0 README template to record the tested invocation.

  4. Verify and save

    10 min

    Save the entry point, README command and fresh summary. Check the command regenerates both required artifacts without undocumented manual steps.

What to save

Invalid-input and failed-child tests return nonzero status; the restored valid command regenerates fresh evidence.

Watch for: Do not mark a wrapper successful merely because subprocesses launched; propagate their failure status.

Check your understanding

Why should the default reproduction command use a tiny fixture instead of the full training run?

Check your reasoning

It makes the core implementation and environment checks affordable and reviewable while leaving the full experiment as an explicit separate command.
