Hour 1 of 2 · 60 minutes

Trace The Official MCP Tool Interface

By the end of this hour

  • Map a workspace tool onto the MCP tool interface.
  • Locate the permission decision that must remain in the host.

Before you begin

  • Your working read or search tool and its argument validation.
  • The disposable workspace boundary from Activity 3.

Environment or workflow question? Day 0 handbook.

The key idea

MCP gives a client and a tool server a common way to describe and invoke capabilities. It does not decide whether your agent should exercise a capability. For this adapter, the important invariant is that both direct calls and protocol calls reach the same validation and permission checks before reading the workspace. Separate the public tool description, argument schema, transport request, and internal implementation. This makes interoperability a small interface exercise while keeping your existing execution boundary understandable and testable.

Your 60-minute plan

  1. Retrieve

    5 min

    Without opening code, sketch the path from a model tool request to a permitted workspace read. Circle where authorization happens.

  2. Study

    10 min

    Use the core resources above for ten minutes in total, focusing only on the indicated sections. Spend 10 minutes on H6-tools: Discovery, invocation, input schema, and tool result. Stop at the time limit and use the page as a reference while building.

  3. Build

    35 min

    Choose exactly one existing read-only tool. Create docs/mcp-contract.md with a table mapping its name, description, argument fields, validation errors, return content, and permission gate to the SDK interface. Use one valid request, one missing required argument, and one disallowed path as concrete examples. Mark the existing host function you intend to call from the adapter; do not duplicate its permission logic. Record the SDK version and local transport selected. Stop before implementing another tool or a new agent loop.

  4. Verify and save

    10 min

    Trace each example through the table. Commit the contract note with a statement that model-provided arguments cannot grant permission.

What to save

Adapter mapping preserves the existing tool contract.

Watch for: Do not move permission checks into the model prompt while adding the adapter.

Check your understanding

If a tool description says “read only,” is the workspace boundary enforced?

Check your reasoning

No. The server or host must enforce the boundary in executable validation before the read; a description is a communication aid, not an authorization mechanism.

Hour 2 of 2 · 60 minutes

Expose One Existing Workspace Tool

By the end of this hour

  • Expose the selected tool through a minimal MCP server.
  • Reuse the existing permission-checked implementation.

Before you begin

  • docs/mcp-contract.md from the previous session.
  • A passing direct invocation of the chosen read-only tool.

Environment or workflow question? Day 0 handbook.

The key idea

An adapter translates between interfaces without becoming a second implementation of the underlying operation. Keep the protocol-specific code thin: parse the request through the SDK, pass validated arguments to the existing host entry point, and translate the result into the SDK result shape. This preserves one source of truth for path confinement and error handling. A successful request proves that the transport works; later sessions will establish that invalid and unauthorized requests preserve the same boundary as direct invocation.

Resources for this hour

Read the indicated section, not the entire source. The core reading fits inside the plan below. A video is an alternative to reading, not extra homework.

  • Core · 10 min · project

Your 60-minute plan

  1. Retrieve

    5 min

    Write the three jobs of the adapter from memory: accept the protocol request, call the existing host boundary, and translate the result.

  2. Study

    10 min

    Use the core resources above for ten minutes in total, focusing only on the indicated sections. Spend 10 minutes on H6-sdk: Minimal server and client examples for installed major version. Stop at the time limit and use the page as a reference while building.

  3. Build

    35 min

    Create a small MCP adapter module around the selected host tool using the official SDK version recorded yesterday. Register only that tool and run the server using your selected local transport. Write a client smoke script that discovers the tool and reads a harmless fixture inside the disposable workspace. Have the adapter call the same host entry point as the direct path. Capture the returned content and request metadata without secrets. Keep model calls out of this plumbing test and defer convenience features.

  4. Verify and save

    10 min

    Run the client twice from a clean start. Save the smoke command, expected fixture content, and SDK pin alongside the adapter.

What to save

MCP tool responds to a valid request.

Watch for: Do not add a second unchecked file-reading implementation inside the MCP adapter.

Check your understanding

Why keep model calls out of the initial MCP smoke test?

Check your reasoning

A deterministic client isolates protocol and adapter behavior. Model choices would introduce an unrelated source of failure and API cost.
