Run The Bounded Recent History Baseline

By the end of this hour

  • Implement a recent-history baseline under the same context ceiling.
  • Compare both policies on fixed development tasks.

Before you begin

  • Use the compact-context implementation and shared evaluator.
  • Select fixed development tasks long enough to activate context selection.

Environment or workflow question? Day 0 handbook.

The key idea

A recent-history baseline should be bounded and valid, not intentionally broken. Preserve the task and constraints, then keep the newest complete message units that fit the same ceiling used by compaction. Both conditions share model, tools, task snapshots, output limits, and overall budgets. If compaction uses extra model calls, include their tokens, latency, and cost in its condition. Measure how often each policy activates; without activation, the trial does not test memory management. This development comparison helps debug the planned intervention before final evaluation.

Your 60-minute plan

  1. Retrieve

    5 min

    State the one intended difference between the two context policies and three conditions that must remain fixed.

  2. Study

    10 min

    Use the core resources above for ten minutes in total, focusing only on the indicated sections. Spend 5 minutes on H18: Context selection as a recurring inference decision. Spend 5 minutes on H8: Shared inference ceilings and charged overhead. Stop at the time limit and use the page as a reference while building.

  3. Build

    35 min

    Implement recent_history_context by retaining the original task/constraints and the newest complete call/result interaction units within the ceiling. Run this and compact_context on the same small development task set through the evaluator. Record model/version, tools, task revisions, ceiling, total-token cap, time cap, and actual usage. Save per-request context size, policy activation count, task grade, and trace path. If you use a model to produce summaries, route those requests through the same usage accounting; for deterministic extraction, record that no summarizer model calls were made.

  4. Verify and save

    10 min

    Save a paired development table and one context payload from each condition after activation. Confirm all reported costs and latency include policy overhead.

What to save

Matched development traces for both policies.

Watch for: A baseline that drops the original task is not a fair recent-history comparator.

Check your understanding

Why must summarizer tokens count against the compaction condition’s resources?

Check your reasoning

They are work required by that policy. Excluding them would give compaction additional unreported inference resources and make cost or budget comparisons unfair.
