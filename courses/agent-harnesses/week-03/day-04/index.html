Implement the Provider Message Adapter

By the end of this hour

  • Translate the raw harness message contract into a provider request.
  • Preserve tool-call/result semantics and account for every outbound request.

Before you begin

  • The raw FakeModel loop, strict tool dispatcher, shared evaluator, and verified execution boundary.
  • Use one provider with a documented tool interface; the worked reference is the official Anthropic Python SDK. An alternative provider needs equivalent tests.

Environment or workflow question? Day 0 handbook.

The key idea

An SDK transports requests; your harness still owns the loop. A real response may contain text, multiple tool calls, provider-specific continuation data, a stop reason, and usage fields. Reducing that response to one string loses information needed by the next turn. Keep a provider representation alongside your normalized records, validate proposed actions, and return each result using the correct call ID. Today builds the adapter against offline fixtures. The next budget lesson authorizes the first small live call only after reservation tests pass.

Your 60-minute plan

  1. Retrieve

    5 min

    Draw the raw request, provider response, validated tool call, and provider tool-result message. Mark identifiers that must survive translation.

  2. Study

    10 min

    Use the core resources above for ten minutes in total, focusing only on the indicated sections. Spend 4 minutes on H9: Client request, retries, timeout, response metadata. Spend 6 minutes on H9-tools: Complete tool-use blocks and matching tool results. Stop at the time limit and use the page as a reference while building.

  3. Build

    35 min

    Create harness/provider.py behind the FakeModel interface. Serialize task, system instructions, tool schema, and prior messages for one chosen model. Preserve complete provider-required response blocks and normalize tool IDs, stop reason, model/request identifiers, and available usage. Configure explicit timeouts and disable automatic SDK retries so the harness can count attempts. Start with one tool call per response if supported; otherwise handle all calls sequentially and return every result, or reject an unsupported multi-call response before any tool executes. Use synthetic provider fixtures for final text, one tool call, two tool calls, and output-limit termination. Treat truncated output as a distinct bounded outcome. Keep the API key outside logs and task containers; do not make live requests today.

  4. Verify and save

    10 min

    Run the offline adapter cases through the existing loop. Save a sanitized request/response/tool-result example and SDK/model configuration. Confirm the HTTP spy records no network calls in this test mode.

What to save

A tested adapter preserves tool IDs, content blocks, stop reasons, and usage without making live calls.

Watch for: Do not treat an output-length stop as successful task completion, or silently execute only the first call in a multi-call response.

Check your understanding

Why not keep only the first text field of a provider response?

Check your reasoning

The response may include tool calls and provider-required continuation blocks. Dropping them breaks message causality and can make the next request invalid; a text string is not the full protocol state.
