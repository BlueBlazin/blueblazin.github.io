Enforce Budgets and Verify the Live Adapter

By the end of this hour

  • Account for model usage, elapsed time, and failure causes.
  • Apply the same externally enforced budgets to both future runners.

Before you begin

  • Use TrialResult and run_trial() from Activity 5, step 1.
  • Complete the provider adapter bridge with offline protocol tests. Keep credentials host-side and do not make paid calls until this lesson’s reservation tests pass.

Environment or workflow question? Day 0 handbook.

The key idea

A fair harness comparison must specify the resources each system is allowed to spend. The same model name is not enough when context limits, output limits, retries, or tool budgets differ. Capture provider-reported usage where available and compute estimated charges using a recorded price table; the estimate is not a bill. Enforce the common limits outside both runner adapters when possible. A run that reaches a limit is still an attempted trial, with a failure reason and the usage incurred before stopping.

Your 60-minute plan

  1. Retrieve

    5 min

    List four settings other than model name that can make two harness runs receive unequal resources.

  2. Study

    10 min

    Use the core resources above for ten minutes in total, focusing only on the indicated sections. Spend 5 minutes on C5: Chosen model rates and enabled billable features. Spend 5 minutes on H9: Disable retries; preserve unknown-usage errors. Stop at the time limit and use the page as a reference while building.

  3. Build

    35 min

    Implement TrialBudget with request count, deadline, input/context ceiling, output limit, and total token/spend caps. Before dispatch, reserve a conservative maximum for the full input, bounded output, and enabled billable features using the recorded price table; refuse a request that does not fit. With a single sequential dispatcher, persist reservation and attempt ID before sending, then settle against available usage. Retain the full reservation after unknown-usage timeouts until reconciled. Set SDK retries to zero so later harness retries each pass this gate. Count malformed responses and failed requests as attempts. Test near-exhaustion, unknown usage, and rejected extra calls with a fake client; record missing usage as unknown.

  4. Verify and save

    10 min

    After fake cap tests pass, run one tiny live read-only development loop with explicit request/output/deadline limits. Save the tool-call/result payload and usage provenance. If credentials or caps are blocked, retain the offline passing tests and defer live-dependent lessons to flex time.

What to save

Fake budget enforcement tests and a bounded provider smoke trace, or explicit live blocker.

Watch for: A budget checked only after an expensive request cannot prevent that request from exceeding the intended spend cap.

Check your understanding

Why is missing token usage different from zero token usage?

Check your reasoning

Missing usage means the amount is unknown. Zero asserts that no tokens were consumed and can understate cost or make comparisons misleading.
