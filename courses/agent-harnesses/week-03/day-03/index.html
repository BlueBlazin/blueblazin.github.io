Build Clean Workspace Outcome Evaluation

By the end of this hour

  • Separate agent execution from host-side outcome grading.
  • Grade clean reference and no-op runs reproducibly.

Before you begin

  • Use the validated eight development fixtures and their host-only graders.
  • Retain a pinned fixture revision and the execution boundary from Activity 3.

Environment or workflow question? Day 0 handbook.

The key idea

An evaluator orchestrates a trial without trusting the agent’s own success claim. It starts from an immutable fixture revision, runs the selected harness, and grades the resulting workspace with checks the agent cannot edit. Execution and grading should have separate interfaces so multiple harnesses can share the same evaluator. A clean copy prevents a previous trial’s successful edit from contaminating the next trial. Record the fixture revision and grader version with each result; a task id alone is insufficient when its files can change. Host-owned grading means the controller and trusted checks are protected from agent writes. It does not mean importing or executing agent-modified code in the host Python process. Any dynamic behavioral check runs that code in a fresh bounded grading container with no credentials; the host may safely compare inert output data.

Your 60-minute plan

  1. Retrieve

    5 min

    Sketch the boundary between the task workspace, the agent runner, and the host-only grader. Mark which data each may modify.

  2. Study

    10 min

    Use the core resources above for ten minutes in total, focusing only on the indicated sections. Spend 5 minutes on H7-verifier: Trusted verification runs after candidate execution. Spend 5 minutes on H22: Independent temporary task copies. Stop at the time limit and use the page as a reference while building.

  3. Build

    35 min

    Create eval/evaluator.py with a run_trial(task_id, runner, config) entry point. Load the pinned fixture, create a new workspace, run the supplied runner, then invoke the host-side grader against the result. Return a structured TrialResult instead of scraping console text. First supply two simple runners: one applies the known reference patch and one does nothing. Include fixture hash, grader version, runner name, and outcome in the result. Keep agent-written tests out of the trusted grading path unless the grader explicitly verifies them. For a grader that runs student-generated Python, execute the candidate in the isolated runner or a fresh grading container with trusted checks mounted read-only and no secrets, then collect bounded results. Never import candidate modules into the host evaluator.

  4. Verify and save

    10 min

    Run reference and no-op trials for two different development tasks. Confirm fresh workspace paths and the expected pass/fail grades; save the result JSON.

What to save

Reference and no-op runs produce expected grades.

Watch for: Running only tests supplied or modified by the agent can let an incorrect edit redefine success.

Check your understanding

Why should two harnesses share one evaluator?

Check your reasoning

It holds task initialization, grading, and result accounting constant. Otherwise measured differences may come from different evaluation conditions rather than the harnesses.
