Integrate and Inspect the Baseline Harness

By the end of this hour

  • Integrate a pinned mini-SWE-agent with the shared development evaluator.
  • Record interface differences that prevent a one-variable policy comparison.

Before you begin

  • Use the shared evaluator, tested provider adapter, enforced budget reservations, and verified isolated execution runner.
  • Pin mini-SWE-agent and inspect its actual model, environment, and command interfaces.

Environment or workflow question? Day 0 handbook.

The key idea

A baseline should remain recognizable. mini-SWE-agent uses a command-oriented interface, while your course harness has typed read/search/write tools. Matching model, tasks, environment restrictions, and resource ceilings does not erase this interface difference. Treat this early exercise as a descriptive comparison between two systems, not an isolated test of context policy. A thin adapter lets both systems share task initialization and grading without pretending their prompts and available actions are identical. The later within-harness study will hold those factors fixed.

  2. Study

  3. Build

    35 min

    Create the baseline adapter using the pinned mini-SWE-agent entry point. Give it the same task snapshot, model configuration where supported, isolated runner restrictions, deadline, and token/spend ceilings. Disable hidden transport retries or include them in accounting. Retain its documented command interface and list differences from your typed tools and system instructions. Run a mocked transport/configuration smoke test on one development fixture; perform a bounded live check only after the common budget gate passes. Do not spend this hour authoring final fixtures. If a shared limit cannot be enforced, mark the comparison blocked until fixed rather than relabeling unlike runs as matched.

  4. Verify and save

    10 min

    Save the adapter smoke trace and a comparison-conditions table listing common limits and differing interfaces. Confirm no final-task agent run occurred.

What to save

Runnable baseline adapter and an honest comparison-conditions table.

Watch for: Do not replace the baseline interface with your own and then describe the result as an unchanged mini-SWE-agent baseline.

Check your understanding

Can this pilot isolate a context-policy effect if the baseline uses a different tool interface?

Check your reasoning

No. It compares complete systems under recorded constraints. Interface and prompt differences are confounds; the later experiment changes only context policy inside your own harness.

Compare Two Systems Under Declared Limits

By the end of this hour

  • Run two systems through one budget-controlled development command.
  • Explain outcomes with saved traces and disclosed interface differences.

Before you begin

  • Use the mini-SWE-agent adapter, your raw harness adapter, and shared budget configuration.

Environment or workflow question? Day 0 handbook.

The key idea

The development pilot checks integration and exposes useful behavior differences. Use the same task snapshots, model configuration where supported, environment restrictions, and resource ceilings, then preserve every attempted run. Keep the baseline interface recognizable and report differences in its tools, prompts, and stopping conventions. Equal ceilings do not imply equal actual consumption. Two tiny tasks cannot rank systems generally or isolate one mechanism; they can reveal an adapter error or demonstrate how different interfaces approach the same problem.

What to save

Watch for: Do not silently discard a baseline timeout because your own harness completed the same task.

Check your understanding

Can two development tasks establish that one harness is generally superior?

Check your reasoning

No. They test integration and expose useful behavior differences. General claims require a larger, well-controlled held-out evaluation and uncertainty reporting.
