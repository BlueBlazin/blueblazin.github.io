Add Writes And Structured Traces

By the end of this hour

  • Add a bounded workspace write tool.
  • Record inspectable calls, results, time, and explicitly labeled cost.

Before you begin

  • Use the confined read/search tools and path resolver from Activity 2, step 1.

Environment or workflow question? Day 0 handbook.

The key idea

A useful trace should explain what the harness attempted and what actually happened without requiring reconstruction from console prints. Record the run id, tool-call id, validated arguments, status, result summary, and elapsed time. Cost is a measurement with provenance: fake-model runs have no API charge, while estimated charges must be labeled estimates. Writes introduce side effects, so keep their semantics narrow and observable. Replacing the entire contents of a small file is easier to inspect than accepting an unrestricted shell command.

Your 60-minute plan

  1. Retrieve

    5 min

    Specify whether your write tool creates missing files, overwrites existing files, or both. State how an invalid path should appear in the trace.

  2. Study

    10 min

    Use the core resources above for ten minutes in total, focusing only on the indicated sections. Spend 5 minutes on H19: File-edit interfaces and useful response content. Spend 5 minutes on H29: Monotonic elapsed-time measurement. Stop at the time limit and use the page as a reference while building.

  3. Build

    35 min

    Implement write_file(path, content) using the same workspace resolution and size limit as read_file. Restrict the exercise to a disposable workspace and choose clear behavior for missing parent directories. Add a trace collector around dispatch that records call id, arguments, outcome, start/end times from a monotonic clock, and cost_kind. Script a fake-model read/write/read sequence that changes one configuration value. Record fake-model API cost as zero with cost_kind=mock; do not disguise a token estimate as a provider bill.

  4. Verify and save

    10 min

    Run the scripted sequence and inspect the resulting file diff and trace. Save a compact JSON trace showing both the original read and the verified written content.

What to save

Readable trace from a read/write scenario.

Watch for: Do not allow a failed write to be recorded as success merely because the dispatcher returned normally.

Check your understanding

Why should the final read be part of this fixture?

Check your reasoning

It checks the observable effect of the write rather than assuming a successful return value implies the intended file contents were produced.

Outline Tasks And Build Fixtures

By the end of this hour

  • Separate development tasks from final evaluation tasks.
  • Create three small reproducible development fixtures with outcome checks.

Before you begin

  • Use the working workspace tools; create a host-only evaluation directory outside agent-writable task roots.

Environment or workflow question? Day 0 handbook.

The key idea

An agent task needs an initial state, a user-facing request, and an outcome check that can distinguish success from a plausible-looking answer. Development tasks guide implementation; final tasks must not become another debugging set. Authoring the tasks yourself does not make them blind, so describe this as a held-out development split. Begin with small transformations whose correct result is deterministic. Keep reference solutions and graders outside the task workspace so the model cannot obtain a passing result by reading or modifying them.

Your 60-minute plan

  1. Retrieve

    5 min

    For a request to change a configuration value, describe a final answer that sounds successful but leaves the task unsolved.

  2. Study

    10 min

    Use the core resources above for ten minutes in total, focusing only on the indicated sections. Spend 6 minutes on H4: Tasks, outcomes, and objective grader criteria. Spend 4 minutes on H22: Fresh per-test workspace directories. Stop at the time limit and use the page as a reference while building.

  3. Build

    35 min

    Create eval/manifest.json with 24 stable ids, split labels, short requests, task family, and fixture paths. Reserve sixteen final ids without running an agent on them. Implement dev-01 as a configuration edit, dev-02 as a small text/data repair, and dev-03 as a tested function correction. Keep each fixture tiny enough to inspect in minutes. Add a fresh-copy helper and one deterministic outcome check per task. Save reference outputs or patches in the host-only evaluation directory; do not add them to the copied workspace.

  4. Verify and save

    10 min

    Instantiate all three development workspaces twice and compare their starting contents. Run each grader on the original fixture and its reference solution to check that the intended change is detectable.

What to save

Task manifest and three reproducible fixtures.

Watch for: Renaming a development task without changing its underlying task family provides weak held-out evidence.

Check your understanding

Why is a self-authored final split not a blind independent benchmark?

Check your reasoning

You know how the tasks were constructed and may share assumptions with them. Holding out agent outcomes helps prevent tuning leakage but does not remove author knowledge or establish external validity.
