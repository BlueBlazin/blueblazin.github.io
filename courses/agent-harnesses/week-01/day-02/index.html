Validate Typed Tool Call Arguments

By the end of this hour

  • Validate a tool call before dispatch.
  • Produce reproducible valid and malformed fake model responses.

Before you begin

  • Use Day 1’s tiny FakeModel loop and docs/loop-contract.md. Replace the loose observe dictionaries with the strict tool-call contract developed today.

Environment or workflow question? Day 0 handbook.

The key idea

A tool schema is a contract between untrusted proposed arguments and trusted execution code. Parsing JSON only establishes syntax: the host must also reject unknown tools, missing fields, unexpected fields, wrong types, and values outside the supported domain. Keep these checks outside the tool implementation so a malformed request cannot partly execute. A deterministic fake model lets you test this interface without API variability or cost. Give each tool call an identifier that its result will carry, making later message pairing unambiguous.

Your 60-minute plan

  1. Retrieve

    5 min

    List three malformed inputs that still qualify as valid JSON. Predict whether any should reach the dispatcher.

  2. Study

    10 min

    Use the core resources above for ten minutes in total, focusing only on the indicated sections. Spend 6 minutes on H19: Tool descriptions and explicit input/output contracts. Spend 4 minutes on H17: One parametrized input/expected-outcome matrix. Stop at the time limit and use the page as a reference while building.

  3. Build

    35 min

    Create harness/contracts.py with a ToolCall record containing id, name, and arguments. Implement one harmless echo tool that accepts exactly one string field named text. Use a dataclass plus explicit checks, or a strict validation library already in your project. Add FakeModel backed by a finite list of scripted responses. Write fixtures for a valid echo, missing text, integer text, extra field, and unknown tool. Add a dispatcher spy or counter so tests can prove rejected calls never execute a tool.

  4. Verify and save

    10 min

    Run the focused validation tests. Save the accepted normalized call and the structured rejection reasons; verify the dispatch counter remains zero for every invalid fixture.

What to save

Valid and malformed tool-call fixtures.

Watch for: Some validators coerce integers into strings by default; choose strict behavior deliberately.

Check your understanding

Why is JSON parsing insufficient validation?

Check your reasoning

Syntactically valid JSON can contain unsupported tool names, wrong field types, missing arguments, or invalid values. Execution requires the narrower application contract.
