Connect Tool Results To Messages

By the end of this hour

  • Connect validated calls to tool results and the next model response.
  • Return structured terminal outcomes for successful and failing tools.

Before you begin

  • Use FakeModel, strict ToolCall validation, and the echo dispatcher from Activity 1, step 2.

Environment or workflow question? Day 0 handbook.

The key idea

The model/tool loop is a sequence of observable records. Each tool call must be followed by a result associated with the same identifier, and the next model invocation must see that result. Otherwise the model is continuing with an incomplete account of the world. Keep tool failures separate from final answers: an exception can become a structured error observation or a terminal failure according to your chosen policy. For this first implementation, make that policy explicit and deterministic rather than adding automatic retries.

Your 60-minute plan

  1. Retrieve

    5 min

    Reconstruct the message sequence for user request, tool call, tool result, and final answer. Add call identifiers.

  2. Study

    10 min

    Use the core resources above for ten minutes in total, focusing only on the indicated sections. Spend 10 minutes on H9-tools: Tool identifiers and response/result message ordering. Stop at the time limit and use the page as a reference while building.

  3. Build

    35 min

    Extend the Day 1 run() stub in harness/loop.py with the validated tool states. Append the model response, validate its call, dispatch echo, and append a result with the matching call id before requesting the next scripted response. Represent a final answer as a terminal record with status, answer, and step count. Add a second fake tool that raises a controlled exception. Convert that exception into your documented error outcome while preserving a useful error type and a sanitized message. Do not add live API transport today.

  4. Verify and save

    10 min

    Run one echo-to-answer scenario and one raising-tool scenario. Save both message traces and assert that the fake model receives the tool result before it produces the answer.

What to save

Successful tool scenario and exception trace.

Watch for: Do not serialize credentials or whole exception objects into model-visible error messages.

Check your understanding

What goes wrong if the loop calls the model again without appending the tool result?

Check your reasoning

The next response lacks the observed outcome and may repeat the action or invent a result. The host must preserve the causal call/result sequence.
