Day 0 · Setup & course handbook

Prepare only the tools needed for your first lab, then begin Day 1 with a working FakeModel loop. All setup, review and course-administration material lives here. Later-use checklists are references for their stated milestones, not prerequisites to complete now.

Get ready, then start building

This is a reference and readiness page, not a mandatory study day. Complete only the setup you need, then continue to Day 1 in the same session if time allows. Later review and portfolio instructions are filed below for when their prerequisites exist.

  • Comfort writing and testing Python programs, using Git, and reading JSON.
  • Basic familiarity with HTTP APIs and language-model messages; no model-training experience is required.
  • A local Python environment on the M1 Max and willingness to use a local container runtime for controlled execution tests.
  • No architecture course, kernel course, NVIDIA GPU, or trained model is required.

Local repository and Python

Create agent-harness-lab with harness/, tests/, fixtures/, evals/, docs/, reports/, and scripts/. Create or reuse a Python virtual environment and install pytest. Run a minimal import/JSON smoke test. Ignore credentials, environments, generated workspaces, and private runtime traces. Python and pytest are sufficient for Day 1. Install and pin provider/MCP SDKs from this setup reference before the lessons that actually use them.

Report, demonstration, and release templates

Populate these templates incrementally from completed work. Leave future-result fields empty. Writing and presentation are reference guidance rather than standalone lesson days.

Report (2–4 pages): question; harness design; the two context conditions; task suite; limits and metrics; audited main results; failure analysis; limitations. Every numerical claim links to an authoritative table or trace and the frozen manifest. A neutral or negative result is a valid outcome.

README reproduction path: prerequisites; exact pinned dependency and model versions; setup commands; credential variable names without values; a bounded fake-client or development smoke command; expected output paths and success criteria. Document the full 96-attempt study command separately with its exposure estimate. A smoke run does not reproduce the full statistical result.

Evidence index columns: claim; frozen code/configuration; command; smallest supporting trace or table; limitation. Suggested rows: termination, execution boundary, resume reconciliation, MCP parity, context policies, attempt accounting, cost, uncertainty. Separate development, final, and optional external results.

Demonstration checklist: use existing clean development fixtures for success, restart, and bounded failure; show run ID, decisive event, terminal status, and outcome evidence; label fake responses. A terminal transcript is sufficient.

Release checklist: verify links and scope, remove credentials and unintended private traces, record a release commit, state the 16-task/two-condition/three-attempt design and actual outcome, and keep follow-up work separate. Publish only under your chosen visibility and license.

Contribution checklist: consult the project contribution guide; reduce the problem to a minimal reproducible case; include expected and observed behavior, versions, and a focused regression test. Drafting is sufficient for the course; sending an issue or pull request is optional.

Prepare the Standalone Harness RepositoryBefore Day 1 / when setup is needed

Repository/environment creation belongs in Day 0.

This course produces one independent software artifact: a small coding-agent harness and its evaluation evidence. Most work runs locally, with deterministic fake model responses used before paid API experiments. Keeping code, task fixtures, reports, and generated traces distinct makes failures easier to reproduce and the eventual portfolio easier to inspect. Start with the smallest environment that can run ordinary Python tests. Provider integration and process isolation arrive in later labs; today establishes the reproducible workspace those labs will use.

  • Python, Git, and a terminal on your Mac. No GPU or other course repository is required.
  1. Retrieve

    Write down what you expect a reviewer to need to run a small Python project from a fresh clone. Identify which items are machine-specific.

  2. Study

    Read H2 on starting with simple agent systems. Inspect the course outcome and note that model calls, tool execution, and outcome grading are separate responsibilities.

  3. Build

    Create a new repository named agent-harness-lab. Create the course directories:

    Choose one Python environment workflow, install a test runner, and record the exact Python and package versions. Add a minimal test that imports your package and round-trips a small JSON object. Add ignore rules for the environment, credentials, runtime traces, and generated task directories. Write README setup instructions and docs/environment.md with your OS, Python version, test command, and dependency export or lockfile. Do not implement the agent loop yet.

  4. Verify and save

    Open a fresh shell, activate the recorded environment, and run the smoke test using the README. Commit source and setup files after confirming no credentials or generated task state are staged.

Reference checklist

  • A fresh shell can follow the README and pass the smoke test.
  • Dependency versions and local environment details are recorded.
  • Source, fixtures, evidence, and ignored runtime files have explicit locations.
Self-check

Why begin with fake model responses rather than connecting a paid model immediately?

Deterministic responses let you verify host control flow and tests without API cost, provider availability, or model variability obscuring ordinary software errors.

Set the Evaluation and Spending Ground RulesBefore Day 1 / when setup is needed

Evaluation policy and spending ledger belong in the shared guide.

An agent may sound confident while leaving a repository incorrect. This course therefore measures observable task outcomes and treats the evaluator as software that needs its own controls. Eight development tasks support debugging; sixteen final tasks are reserved for the frozen comparison. You will build these fixtures later, so this hour establishes the rules rather than inventing the whole benchmark. The required final study has two context policies and three attempts per final task, with failures retained and resource limits matched.

  • The standalone repository and working local test command from onboarding.
  1. Retrieve

    Describe one coding task that an agent could claim to finish while doing nothing useful. Name an observable condition that would distinguish success.

  2. Study

    Read H4 on tasks, trials, outcomes, and graders. Skim the shared compute guidance for API accounting; do not choose an expensive model or purchase a GPU.

  3. Build

    Write docs/evaluation-charter.md. For a toy task outside the future benchmark, such as changing a function to handle an empty list, specify a successful outcome, a reference solution, a no-op, and a broken solution; predict their grades without building the full runner. Record the planned 8-development/16-final split, the ban on final-agent-result-driven tuning, and the 16×2×3=9616\times2\times3=9616×2×3=96-attempt study. Create a spending ledger with chosen currency, a personal API allowance within the total study budget, and fields for reservations and actual charges. Record how you will supply secrets at runtime and which local container runtime you will inspect before the execution-boundary module.

  4. Verify and save

    Check that a no-op cannot satisfy the toy task. Save the charter and ledger template. Confirm that no model calls or held-out agent runs were needed for this session.

Reference checklist

  • The toy example distinguishes a reference pass from no-op and broken failures.
  • The task split, 96-attempt calculation, and held-out boundary are written.
  • API allowance, ledger fields, and runtime-secret handling are recorded.
Self-check

Does inspecting final-task fixture controls contaminate the same evidence as tuning prompts after seeing final-agent failures?

No. Validating written fixtures and reference/no-op controls checks the measuring instrument. Tuning the harness from final-agent outcomes adapts the system to its final exam; those outcomes must remain unseen until the design is frozen.

Repair a blocker or consolidateUse later · after the relevant labs

A pacing contingency is not a subject lesson.

Flex time absorbs normal uncertainty in engineering work. Select one problem whose resolution unblocks later learning: a failed numerical check, an unclear derivation, a broken environment or missing evidence. Diagnose before changing code. A small reproducible example is often a better outcome than many speculative edits. When your work is current, use a brief retrieval check and finish early. This is spare capacity inside the course, not a requirement to invent another hour of work. Sunday stays free.

  • Open your unfinished lesson checklist and the most recent failing check.
  • If nothing is blocked, choose one concept from the preceding week to recall.
  1. Select one target

    Inspect unfinished checklist items. Choose the earliest prerequisite blocker and write the current versus expected behavior. If there is no blocker, name one concept to recall.

  2. Choose the smallest check

    Identify the smallest input, test or worked example that could distinguish your two most likely explanations. Avoid launching cloud hardware until it is actually needed.

  3. Repair or consolidate

    Reproduce the failure, change one thing at a time, and rerun the check. Save the useful evidence even if the repair remains incomplete. If current, reconstruct a recent mechanism without notes, check it and finish early. Do not start optional frontier work solely to fill this slot.

  4. Close the loop

    Return to the original lesson and check its completion item only if it now passes. Record the remaining blocker and the exact next command or question. If it blocks the next lesson, shift the calendar instead of scheduling Sunday catch-up.

Reference checklist

  • Chose one prerequisite blocker or completed a short retrieval check.
  • Saved a repair, a useful minimal reproducer, or a corrected explanation.
  • Updated the original lesson status and wrote the next action; finished early if current.

What if the blocker is still unresolved at the end?

Preserve the smallest reproducer and the hypotheses already ruled out. Defer dependent work or use the next flex session. Extending the calendar is preferable to hiding a correctness failure or exceeding the daily time budget.

Assessment: Resume and Context PoliciesUse later · after the relevant labs

Keep restart/context assessment as an on-demand milestone reference.

State persistence and context selection solve different problems. A durable log can preserve the full history, while the next model request must fit a finite context budget. Restart additionally has to establish what actually happened in the workspace. This review makes those distinctions executable: inspect an interrupted write, then inspect the model-visible payloads of two policies under one limit. The objective is a narrow demonstration of the declared contracts, not a claim of exactly-once execution or universal memory reliability.

  • The evaluator, bounded navigation, persisted state, restart tests, and two context policies from modules three and four.
  1. Retrieve

    Answer closed-book:

    (1) Why can an atomic checkpoint still leave an uncertain write?

    1. What should a third file hash mean during before/after reconciliation?
    2. Which context and accounting constraints must both policies share?
  2. Study

    Score each answer 0–2 using the self-check and your recorded contracts. Reopen only the relevant restart or compaction note for the weakest answer.

  3. Build

    Use your existing interruption hook to stop after a single-file replacement but before completion is saved. Restart from the checkpoint and verify that reconciliation performs no second write when the after-hash matches. Then feed one long development history to both context policies at the same ceiling. Inspect the original task, complete call/result units, activation logs, and retained evidence. Record any compaction-model overhead in the same budget fields as task-model work. Preserve one fact that compaction retained and one it lost or deliberately omitted.

  4. Verify and save

    Save reports/review-module-4.md with score, restart trace, payload references, and one unsupported generalization. Target 5/6 with no zero on uncertain-side-effect handling; carry gaps to flex time.

Reference checklist

  • Closed-book answers are scored and corrections saved.
  • The already-applied replacement is reconciled without another write.
  • Both payloads respect one ceiling and account for policy overhead.
Self-check

What are the answers to the three assessment questions?

  1. Checkpoint persistence and the workspace mutation are separate operations, so a crash can occur between them.
  2. A hash matching neither before nor intended after indicates conflict or uncertainty; stop for reconciliation rather than overwriting it blindly.

Draft The Harness Experiment ReportUse later · after the relevant labs

Report presentation instructions become a reusable template.

A strong report lets a reader reconstruct the question, intervention, measurement, and conclusion without browsing the whole repository. Lead with the concrete experiment rather than a list of technologies. Explain the harness only to the depth needed to understand context handling, tool execution, budgets, and persistence. Then show the frozen comparison and its audited results. Keep the main narrative short enough to read in one sitting, with raw traces and detailed tables linked as evidence rather than pasted indiscriminately into the text.

  • Audited result tables, experiment plan, failure analysis, and limitations.
  • The harness architecture and frozen implementation references.
  1. Retrieve

    Give a thirty-second explanation of the problem, changed variable, measured outcome, and largest limitation.

  2. Study

    Review your experiment plan and audited findings. Choose the one table or figure that most directly answers the original hypothesis.

  3. Build

    Create reports/harness-report.md, targeting two to four pages of equivalent Markdown. Draft sections for question, harness design, two conditions, task suite, limits and metrics, main results, failure analysis, and limitations. Explain the context ceiling and how compaction overhead is charged. Link the frozen manifest and authoritative result tables. Include one representative evidence-loss or recovery example, clearly labeled as illustration. Use actual measured numbers or explicit placeholders referencing the source table; do not invent a favorable summary to make the draft look finished.

  4. Verify and save

    Read the draft once as a reviewer. Confirm every numerical claim has a source and the conclusion fits the audited result.

Reference checklist

  • The draft explains the question, intervention, controls, and outcome measure.
  • Main results link to audited tables and frozen experiment records.
  • One clear limitation accompanies the headline finding.
Self-check

Why is a list of frameworks insufficient as the report’s main story?

It describes ingredients but not the engineering question, measured behavior, or evidence that the implementation works under its stated limits.

Add Reproduction Commands Traces And CostsUse later · after the relevant labs

Documentation of existing commands becomes a reusable reproduction checklist.

Reproduction instructions are an executable claim. A reader needs prerequisites, pinned versions, configuration, required environment variable names, the command to run, and the expected artifact—not your private account credentials. Distinguish a small smoke or development reproduction from the expensive full ninety-six-trial study. The small path should exercise the important harness behavior with bounded cost and clear outputs. Link complete study records so readers can inspect the measured result without paying to recreate the entire experiment before understanding it.

  • The report draft and frozen experiment manifest.
  • A clean environment setup path and a low-cost development reproduction command.
  1. Retrieve

    List what a fresh reader needs before running your command. Identify which values are public configuration and which are private credentials.

  2. Study

    Inspect the actual setup and runner entry points. Compare the report’s proposed commands with the frozen manifest and dependency lock.

  3. Build

    Add a reproduction section with exact setup commands that match your repository, environment variable names without secret values, dependency/model revisions, and a bounded development or fake-client smoke command. State the expected output paths and success criteria. Add a separately labeled command for the full frozen study with its estimated exposure. Link one successful trace, one failed trace, the restart evidence, result tables, and the complete cost reconciliation. Execute the small path from a clean working directory and fix only documentation or packaging errors that do not change the frozen experiment.

  4. Verify and save

    Save the small reproduction log and verify every report link resolves to a committed or intentionally archived artifact.

Reference checklist
