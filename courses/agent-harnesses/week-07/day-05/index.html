Recover From Stale Summaries And Restarts

By the end of this hour

  • Detect a summary that omits newer persisted evidence.
  • Resume a run without blindly replaying an uncertain mutation.

Before you begin

  • Persisted run state and restart logic from Activity 7.
  • Evidence-preserving compaction records from Activity 8.

Environment or workflow question? Day 0 handbook.

The key idea

A summary is a derived view of run history, so it can become stale when later events or workspace changes are missing. Durable evidence should let the harness detect that mismatch and rebuild the view or stop clearly. A restart is especially delicate near a mutating tool call: the last saved event may say “started” even though the operation completed before the process died. Recovery should reconcile the actual workspace with persisted intent, rather than assuming success or repeating the action blindly.

Your 60-minute plan

  1. Retrieve

    5 min

    Describe the ambiguous window between a tool starting and its completion event becoming durable.

  2. Study

    10 min

    Use the core resources above for ten minutes in total, focusing only on the indicated sections. Spend 5 minutes on H5: Re-establish actual progress after interruptions. Spend 5 minutes on H23: Inject stale state and an interrupted function call. Stop at the time limit and use the page as a reference while building.

  3. Build

    35 min

    Create a short deterministic run, save a summary, then append a newer tool-result event or workspace change without refreshing the summary. Restart from that checkpoint and require a visible stale-summary decision. Next interrupt a disposable mutating operation after it starts but before its completion is recorded. On resume, inspect a concrete effect such as a marker or expected file content and reconcile the operation before proceeding. Save the old summary, durable events, workspace observation, and recovery choice. Keep both tests independent of live model behavior.

  4. Verify and save

    10 min

    Rerun both scenarios from fresh fixtures. Save traces showing stale-state detection and reconciliation rather than duplicate execution.

What to save

Recovery traces expose stale or uncertain state.

Watch for: Do not assume a missing completion event means the mutating tool never ran.

Check your understanding

Why is a summary timestamp alone insufficient to prove correctness?

Check your reasoning

It may not identify exactly which events and workspace version the summary includes. Evidence pointers or sequence/version fields support a concrete comparison.
