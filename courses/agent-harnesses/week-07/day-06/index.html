Verify The Complete Recovery Failure Matrix

By the end of this hour

  • Run the complete injected-failure matrix.
  • Document supported recovery behavior and unresolved uncertainty.

Before you begin

  • Timeout, rate-limit, malformed-call, crash, stale-summary, and restart tests.
  • The current retry limits, cancellation behavior, and durable event schema.

Environment or workflow question? Day 0 handbook.

The key idea

Recovery is a collection of conditional decisions, not a universal promise that the agent will continue successfully. A useful matrix states whether each failure is transient, permanent, or uncertain; whether execution started; and what the harness does next. The same limits must hold during recovery as during the normal path. Inspecting all cases together exposes inconsistent categories or hidden retry loops. Preserve unsupported cases as explicit limitations instead of hiding them under a generic “recovered” status that cannot be checked.

What to save

Failure matrix distinguishes transient, permanent, and uncertain cases.

Watch for: Do not count a swallowed exception as successful recovery without checking the resulting state.

Check your understanding

Is stopping after an uncertain side effect a recovery failure?

Check your reasoning

Not necessarily. A clear bounded stop can be the correct supported behavior when the harness lacks enough evidence to continue safely.

Hour 2 of 2 · 60 minutes

Predeclare The Matched Harness Hypothesis

By the end of this hour

  • State one falsifiable context-policy hypothesis.
  • Specify all variables held equal between the two conditions.

Before you begin

  • Recent-history and evidence-preserving compaction policies.
  • The frozen private task split and working budget controls.

Environment or workflow question? Day 0 handbook.

The key idea

A harness comparison needs a clearly isolated intervention. Here the intervention is how the agent selects context after reaching a shared ceiling: retain recent history or construct an evidence-preserving compacted record. Both conditions keep the original task and constraints, and neither may leave invalid tool-call/result pairs in the request. Matching model, tools, tasks, and run limits reduces alternative explanations. Summarizer calls are part of the compaction policy, so their tokens, latency, and cost must count against that condition’s budget.

Your 60-minute plan

  1. Retrieve

    5 min

    State the single variable being changed and name four variables that must remain fixed.

  2. Study

    10 min

    Use the core resources above for ten minutes in total, focusing only on the indicated sections. Spend 10 minutes on H8: Held-out feedback boundaries and comparable budgets. Stop at the time limit and use the page as a reference while building.

  3. Build

    35 min

    Create evals/experiment-plan.md. Write a directional or two-sided hypothesis about final task success under the same limits. Define the recent-history and evidence-preserving policies precisely enough to identify when each activates and what it retains. List the pinned model identifier, system instructions, tools, fixtures, context ceiling, output limits, run deadline, and cost cap shared across conditions. Explicitly charge compaction calls to its condition. Declare success to be the deterministic task outcome, not an agent claim or a favorable-looking transcript. Do not run final tasks.

  4. Verify and save

    10 min

    Review the two-condition table for unintended differences. Save the hypothesis and a list of development-only checks still needed before freezing.

What to save

Written hypothesis and matched-condition specification.

Watch for: Do not let the baseline drop the original task or break tool-call/result pairing.

Check your understanding

Would using a stronger model only for the compaction condition isolate the policy effect?

Check your reasoning

No. Model quality and policy would both change, so any outcome difference could not be attributed to the context policy alone.
