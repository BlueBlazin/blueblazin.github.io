Exercise Malformed Calls And Tool Crashes

By the end of this hour

  • Reject malformed tool arguments before execution.
  • Record tool crashes and cancellation as bounded terminal or recovery outcomes.

Before you begin

  • Tool validation and execution-boundary tests.
  • The injected model-failure tests from the previous session.

Environment or workflow question? Day 0 handbook.

The key idea

Malformed arguments and tool crashes occur at different boundaries. Validation should reject a bad request before executing a tool; a crash means execution began and may have changed the environment. That distinction matters for retries and recovery. Cancellation should also be visible in the event log and should stop new work from being scheduled. Build the tests around disposable fixtures so the observations are concrete: call counts, workspace changes, process cleanup, and the terminal status the harness reports to its caller.

Your 60-minute plan

  1. Retrieve

    5 min

    Explain why a missing required argument and a tool process crash should have different failure categories.

  2. Study

    10 min

    Use the core resources above for ten minutes in total, focusing only on the indicated sections. Spend 5 minutes on H11: Cancellation propagation and try/finally cleanup. Spend 5 minutes on H13: Terminate and reap real child execution. Stop at the time limit and use the page as a reference while building.

  3. Build

    35 min

    Inject one malformed argument object, one read-only tool crash, and one cancellation while a fake tool is running. Assert that the malformed call never enters the tool body. For the crash, record whether execution started, the exit/error details, and the bounded response chosen by the harness. For cancellation, stop scheduling new calls and confirm the test child process or fake job is cleaned up. Save distinct failure categories. Use tiny fixtures and mocks; do not broaden this into a new general-purpose sandbox implementation.

  4. Verify and save

    10 min

    Run the three tests and save a failure table showing execution started, side effect possible, retry allowed, and terminal outcome.

What to save

Invalid calls and crashes produce bounded outcomes.

Watch for: Do not label all tool exceptions “retryable”; that hides uncertainty about partial effects.

Check your understanding

Can every crashed tool be retried safely?

Check your reasoning

No. A tool may have changed state before crashing. Read-only calls are simpler; mutating calls require evidence or reconciliation before replay.
