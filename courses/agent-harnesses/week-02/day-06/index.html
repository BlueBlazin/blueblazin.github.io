Record Events With Stable Identifiers

By the end of this hour

  • Write an ordered append-only event stream per run.
  • Use stable identifiers and explicit failure categories.

Before you begin

  • Use the existing trace collector and verified execution runner.

Environment or workflow question? Day 0 handbook.

The key idea

An event log records facts as they occur instead of rewriting a single mutable summary. A stable run id groups the trace, while an increasing sequence number establishes order even when timestamps tie. Tool-call ids connect requests to outcomes; task and configuration identifiers make a run interpretable later. Keep protocol status distinct from graded task outcome. A terminal event should explain whether the run completed, was denied, failed validation, hit a limit, or encountered infrastructure trouble without collapsing all cases into “the agent failed.”

  1. Retrieve

    5 min

    Reconstruct a successful tool call as three events: proposed, started, and finished. Which identifiers must connect them?

  2. Study

    10 min

    Use the core resources above for ten minutes in total, focusing only on the indicated sections. Spend 5 minutes on H16: Encoding records; why repeated dump calls need framing. Spend 5 minutes on H4: Separate transcripts from verified outcomes. Stop at the time limit and use the page as a reference while building.

  3. Build

    35 min

    Create harness/events.py with a JSONL writer that appends run_id, sequence, event_type, timestamp, and payload. Give model responses and tool calls stable identifiers within the run. Log run_started, model_response, tool_requested, tool_started, tool_finished, and run_finished for one fixture. Define a small failure enum covering validation, authorization, tool error, timeout, output limit, step limit, and infrastructure. Keep task grading in a separate outcome record. Avoid secrets in arguments or errors; use bounded payloads and paths to larger saved artifacts.

  4. Verify and save

    10 min

    Run one passing fixture and one denied-tool fixture. Validate increasing sequence numbers, unique run ids, paired tool identifiers, and a final event for each run.

What to save

One run produces an ordered event log.

Watch for: Do not overwrite an earlier failure event when producing a friendlier final summary.

Check your understanding

Why retain both sequence numbers and timestamps?

Check your reasoning

Sequence numbers define unambiguous order within a run. Timestamps support duration and cross-system inspection but can tie or vary with clock behavior.

Replay Mock Runs And Inspect Traces

By the end of this hour

  • Replay recorded fake model decisions against fresh fixtures.
  • Inspect a trace without reading raw JSON by hand.

Before you begin

  • Use the append-only JSONL events from Activity 4, step 1 and deterministic FakeModel.

Environment or workflow question? Day 0 handbook.

The key idea

Replay can mean two different things: displaying recorded events, or rerunning recorded decisions against a fresh environment. Be explicit about which you implement. For this lab, replay scripted model responses into a fresh fixture, re-execute permitted local tools, and compare normalized decisions and outcomes. Do not reuse an already mutated workspace or pretend a live model will reproduce identical output. Ignore fields such as wall-clock timestamps when comparing traces, but retain meaningful identifiers, tool arguments, statuses, and resulting file contents.

Your 60-minute plan

  1. Retrieve

    5 min

    Name two trace fields that should differ between replayed runs and two that should remain equal for deterministic fixtures.

  2. Study

    10 min

    Use the core resources above for ten minutes in total, focusing only on the indicated sections. Spend 10 minutes on H14: Scripted side effects and verifying ordered calls. Stop at the time limit and use the page as a reference while building.

  3. Build

    35 min

    Add a replay command that extracts recorded model responses, creates a fresh task workspace, and feeds those responses to FakeModel. Require explicit replay mode and restrict it to the approved disposable local tools. Compare a normalized sequence of tool name, arguments, result status, and workspace output hash with the original run. Add a small CLI formatter that prints step number, event type, tool, status, elapsed time, and truncated result summary. Keep the original event log immutable and save replay events under a new run id.

  4. Verify and save

    10 min

    Replay one successful trace and one controlled error trace. Save the normalized comparison and a sample readable CLI rendering; verify no original run file was changed.

What to save

Deterministic replay and readable inspection.

Watch for: Never blindly replay arbitrary recorded side effects outside the disposable test environment.

Check your understanding

Why must replay preserve a new run id instead of appending to the original run?

Check your reasoning

It is a new execution with its own environment and timings. Reusing the original identity would blur recorded history and could make two tool executions appear to be one.
