Define Durable Agent Run State

By the end of this hour

  • Specify the durable state needed to resume a run.
  • Represent tool action status and workspace version explicitly.

Before you begin

  • Use the event log, RunState, workspace tools, and evaluator developed in earlier harness activities.

Environment or workflow question? Day 0 handbook.

The key idea

A long-running agent needs more than a conversation transcript to resume correctly. Its durable state must connect messages to tool outcomes, remaining budgets, the current workspace version, and any action whose completion is uncertain. Persist only what is needed to reconstruct a valid next transition, but do not assume the latest message reflects the latest filesystem state. A process can crash between mutating a file and recording success. Represent this gap explicitly so restart code can reconcile the workspace instead of silently repeating a side effect.

Your 60-minute plan

  1. Retrieve

    5 min

    Imagine a crash after a write finishes but before its success event is recorded. What facts would a restart need to avoid repeating it?

  2. Study

    10 min

    Use the core resources above for ten minutes in total, focusing only on the indicated sections. Spend 5 minutes on H5: Restore working context from progress and repository state. Spend 5 minutes on H29: Monotonic clock scope versus persisted expiry. Stop at the time limit and use the page as a reference while building.

  3. Build

    35 min

    Create docs/resume-contract.md and a versioned DurableRunState schema. Include run/task/config ids, model messages, completed tool outcomes, step and usage counters, terminal status, workspace snapshot identifier, and current action id/status. Define pending, started, completed, and uncertain action states. For a file replacement, propose expected-before and expected-after content hashes as reconciliation evidence. List which fields come from the event log and which require inspecting the workspace. Sketch restart transitions for no action in flight, completed action, and uncertain mutating action; implementation comes next session. Include in-flight model request IDs and durable budget reservations as well as tool actions. Define a run deadline that does not reset on restart; a process-local monotonic timestamp cannot be reused across processes. For this course, persist a wall-clock expiry plus consumed allowance, use monotonic clocks within each process, and treat expiry or clock inconsistencies conservatively.

  4. Verify and save

    10 min

    Walk one read-only tool and one file-write tool through the schema. Save example state records before and after each, checking that messages and workspace identifiers agree.

What to save

State schema covers each required field.

Watch for: A run id identifies the run, not the workspace contents; retain a separate workspace version or verified content identifier.

Check your understanding

Why can’t the last tool-success message be your only source of truth after a crash?

Check your reasoning

The mutation and the success record may not be committed atomically. The filesystem may have changed before the message was durably saved, leaving an uncertain outcome.
