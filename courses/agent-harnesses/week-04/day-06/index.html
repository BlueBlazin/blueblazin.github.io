Persist Checkpoints Around Tool Actions

By the end of this hour

  • Write durable checkpoints before and after tool actions.
  • Reload messages and workspace metadata without losing action status.

Before you begin

  • Use DurableRunState and the restart transitions from Activity 7, step 1.

Environment or workflow question? Day 0 handbook.

The key idea

Checkpoint placement determines which facts survive interruption. Record an action intent before execution, then record its observed completion after verifying the effect. For a small local prototype, writing a new checkpoint file and atomically replacing the previous file avoids many partial-write problems, but it does not make the checkpoint and workspace mutation one transaction. Preserve an in-flight action record across that gap. Include a schema version and reject incompatible or corrupt checkpoints rather than manufacturing plausible state from incomplete data.

  2. Study

  3. Build

    35 min

    Implement save_checkpoint and load_checkpoint in harness/checkpoint.py using a temporary file and atomic replacement within one directory; document your durability assumptions. Validate schema version and required fields on load. Before dispatching a tool, persist its id, arguments, expected workspace version, and started status. After observing the result, update messages, tool outcome, budget counters, and verified workspace identifier, then save completed status. Exercise this with a harmless read and a single-file replacement. Keep the original event log append-only and link checkpoint records to the last included event sequence. Flush checkpoint writes before replacement. State whether your contract covers only process interruption or also machine/power failure; atomic rename alone does not prove power-loss durability. Recover any in-flight model reservation conservatively rather than resending it for free.

  4. Verify and save

    10 min

    Round-trip a checkpoint and compare all required fields. Simulate an invalid or truncated checkpoint and verify loading fails explicitly rather than resuming with default values.

What to save

Reloaded state matches messages and workspace version.

Watch for: Do not store API credentials in checkpoint state simply because the model adapter uses them at runtime.

Check your understanding

Does atomic checkpoint-file replacement guarantee exactly-once file mutation?

Check your reasoning

No. The checkpoint and workspace mutation remain separate operations. A crash between them can leave an action with an uncertain outcome that must be reconciled.

Resume And Reconcile Uncertain Actions

By the end of this hour

  • Resume completed and read-only actions correctly.
  • Reconcile an uncertain file mutation before deciding to repeat it.

Before you begin

  • Use checkpoint loading and action-state records from Activity 7, step 2.
  • Limit reconciliation to your controlled single-file replacement tool today.

Environment or workflow question? Day 0 handbook.

The key idea

Resume is a decision about the current world, not simply a replay of the last transcript. A completed action should not execute again. A read-only action may be safe to retry under the tool contract, while an uncertain mutation requires evidence. For a controlled file replacement, compare current content with the recorded before and intended after hashes: matching after supports completion, matching before supports nonapplication, and a third value is a conflict. This restricted protocol is understandable and testable; it does not solve arbitrary external side effects.

Your 60-minute plan

  1. Retrieve

    5 min

    For an uncertain write, predict the correct response when the current file matches the before hash, after hash, or neither.

  2. Study

    10 min

    Use the core resources above for ten minutes in total, focusing only on the indicated sections. Spend 5 minutes on H24: Compute a content digest for three-way reconciliation. Spend 5 minutes on H5: Verify the current environment before continuing. Stop at the time limit and use the page as a reference while building.

  3. Build

    35 min

    Implement a resume dispatcher that loads state and branches by action status. Skip completed actions. Restore a recorded observation only if its call/result ID is absent from the loaded messages; never append the same result twice. For an uncertain file replacement, resolve the path again and compute its current hash. If it matches the intended after hash, record reconciled completion without rewriting. If it matches the before hash, allow the documented safe retry. Otherwise stop with a conflict outcome and preserve evidence for inspection. Append a reconciliation event identifying the comparison and decision. Do not generalize this rule to append operations or remote APIs without an appropriate contract.

  4. Verify and save

    10 min

    Create all three hash cases in disposable fixtures. Save a resume trace for each and assert that the already-applied case performs zero additional writes.

What to save

Resume trace documents a reconciled mutation.

Watch for: A changed file might reflect another valid edit; never overwrite a conflict just to make the replay pass.

Check your understanding

What should happen when the current file matches neither recorded hash?

Check your reasoning

The harness should stop or escalate the conflict for deliberate resolution. It lacks evidence that blindly retrying or assuming completion is correct.
