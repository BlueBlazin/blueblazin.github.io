Compare Direct And Protocol Invocations

By the end of this hour

  • Compare direct and MCP invocation on identical cases.
  • Distinguish semantic equivalence from identical wire formatting.

Before you begin

  • The MCP adapter and smoke command from the previous session.
  • The valid, invalid, and unauthorized examples in mcp-contract.md.

Environment or workflow question? Day 0 handbook.

The key idea

The two invocation paths can encode results differently while remaining functionally equivalent. Compare the meaningful outcome: permitted content, validation failure, or permission rejection. A protocol wrapper may add metadata or structure that the direct function does not need. Normalizing those superficial differences makes a useful comparison, but normalizing away an error category would hide a boundary failure. Run the same fixture snapshot and inputs through both paths so that any mismatch can be attributed to the adapter rather than changing workspace contents.

Your 60-minute plan

  1. Retrieve

    5 min

    Predict the outcome category for the three contract examples before executing either path.

  2. Study

    10 min

    Use the core resources above for ten minutes in total, focusing only on the indicated sections. Spend 10 minutes on H6-tools: Protocol errors versus tool execution errors. Stop at the time limit and use the page as a reference while building.

  3. Build

    35 min

    Create a small table-driven test using the same fixture root for direct and MCP calls. Include a valid read or search, a missing required argument, a nonexistent allowed path, and a path outside the permitted workspace. Normalize only transport packaging, then compare content or explicit outcome categories. Assert that rejected requests do not perform a read outside the fixture. Save both raw outputs for one valid and one denied case. Repair translation differences in the adapter without weakening the existing host checks.

  4. Verify and save

    10 min

    Run the matrix from a clean fixture snapshot and save docs/mcp-parity.md with the case table and any deliberate formatting differences.

What to save

Both paths return equivalent outcomes and rejections.

Watch for: Do not compare only the successful read; the denied request is a required parity case.

Check your understanding

Should an adapter turn a permission rejection into an empty successful result?

Check your reasoning

No. That changes the contract and hides why the operation failed. Preserve an explicit denial or error outcome, even if its protocol packaging differs.
